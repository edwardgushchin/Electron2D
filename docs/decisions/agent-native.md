## ADR 0090: Make Electron2D agent-native

Last updated: 2026-10-27

- Status: Accepted by the user on 2026-10-01; live project collaboration, in-editor agent control and replacement of the existing batch interface accepted on 2026-10-25; user workflows, contextual inspection, operation composition, Git-backed project memory, portable instructions, engineering discipline, conventional commits, structured journals, bounded documentation context, editor Git workspaces, bundled skills and an explicit provider/client support list accepted on 2026-10-26.
- Scope: Game and engine development workflows, public API/documentation, project and scene authoring, project Git/documentation/journal ownership, editor automation, batch execution and observable verification.
- Refines: [0004: Product scope](product.md#adr-0004) and [0027: Editor/game boundary](product.md#adr-0027).
- Preserves: [0001: Typed C#](product.md#adr-0001), [0014: Resource lifetime and hot-path allocation](resources.md#adr-0014), [0015: Host lifecycle](core-object-runtime.md#adr-0015), [0016: Scheduling](core-object-runtime.md#adr-0016), [0021: Platform verification](product.md#adr-0021), [0023: Typed packed scenes](scene.md#adr-0023), and [0028: Renderer capabilities](rendering.md#adr-0028).

### Context

Electron2D must be designed and optimized for collaboration with AI coding agents, including Codex, Claude and other clients. An agent needs to understand the applicable contract, modify a project, build it, run a scenario, observe the result, and correct failures. A compiling patch alone cannot establish game behavior or appearance.

The existing typed C# surface, persistence, scene lifecycle, undo history, capture and executable checks provide foundations. Independent file edits and compiled batch runs do not share an editor's unsaved state. The development experience must support a human and an agent working in the same open project, with changes visible in the editor and agent control available inside its window.

### Decision

**Electron2D is an agent-native 2D engine. A live project session is the shared authority for human and agent authoring. The editor provides agent control, while editor UI, external agents and operation clients use the same project operations to create, inspect, modify, build, run and verify a project.** The editor remains usable without an agent. This is an accepted product contract, not a claim that the complete workflow is implemented today.

#### Shared authoring operations and product boundaries

- Project creation/opening, scene/resource/code authoring, validation, import, build, run and export operations must be usable without driving editor widgets. UI and programmatic clients enter the same session operations, validation and persistence rules. A session can run without editor UI; this is the same authoring model with a different host.
- Editor operations belong to the separately shipped editor application under ADR 0027. Development tools may be separate executable consumers under ADR 0004. Portable scene/resource loading, saving and execution belong to their runtime domains and remain part of `Electron2D.dll`. Runtime code never depends on an agent, editor or game assembly.
- The session and its operations are shared editor/tooling responsibilities, with no UI dependency in their executable core. Their assembly layout is established by the first implementation slice; the role names in this decision do not add public runtime types or mandate a new framework, daemon or assembly per service.
- Every first-party editor/tool/game consumes the public runtime API. Missing reusable capabilities must enter their owning runtime slices; agent integration grants no blanket internal access, reflection bypass, backend exposure or duplicate scene/physics/render implementation.
- Documented operation requests/results are independent of their transport. A CLI is an optional client of those operations, not the semantic authority or a separate authoring path. No particular agent, model provider, network service or SDK is required.
- The current `tools/Batch` commands, compiled scenario SDK and version-one request/report formats are not compatibility requirements for this architecture. The session/job implementation may replace and remove them together with their affected consumers and documentation. Reuse executable runtime capabilities and useful checks where they fit; do not add aliases, adapters or a parallel legacy workflow solely to retain this tool interface. This decision does not remove the existing tool by itself.
- C# authoring and scenario programs use ordinary compiled .NET projects and typed APIs. [ADR 0091](scripting.md#adr-0091) selects C# as the only scripting language and one future concrete Script resource, preserving ordinary Node execution and explicit missing binding/authoring capabilities. This decision does not introduce an interpreter or universal runtime invocation system.

The shared live-scene save operation is ResourceSaver.SaveScene under ADR 0013. It projects the authoring host's pre-save/capture/write/post-save lifecycle without requiring editor widgets or a runtime dependency on the editor assembly. Only this explicit authoring operation publishes Node's editor save notifications; ordinary Pack, PackForSave and resource Save retain their existing contracts. This reusable operation does not establish a unified project CLI, visual editor or complete agent workflow.

#### User workflows and editor-independent access

Agent-native means that understanding a project, making a valid change and checking its result are first-class programmatic workflows over the same state and rules used by a human. The agent can discover supported operations, inspect unsaved documents, apply attributed changes, observe conflicts, run a snapshot and retrieve diagnostics and real output. A chat panel alone does not establish this capability.

| User workflow | Interaction surface and state owner |
| --- | --- |
| Human authoring without an agent | The editor's normal views use the live session. No model connection is required. |
| Agent controlled inside the editor | The user supplies a task and context in the editor panel; a replaceable executor invokes shared operations. Human edits continue through the same owner. |
| External agent while the editor is open | The user works in a local Codex or another compatible client. Its tools attach to the open project's owner and observe the same unsaved documents; committed changes appear in normal editor views. |
| External agent without an editor window | An explicit no-UI operation host owns the same session core and jobs. The user interacts entirely through the external client; authoring, history and recovery do not require native editor widgets. |

These are product workflows, with their implemented bounds recorded in the [agent component](../components/project-agent.md). External-client operation needs a reachable, authorized owner and a configured tools connection; opening a conversation alone does not create either. The initial executable host is explicitly started. Automatic startup, installed one-click setup and seamless transfer between a no-UI owner and an editor owner require their own verified lifecycle. Opening the editor must never create a second writer or silently discard the no-UI owner's unsaved state.

A complete no-UI workflow includes explicit saving and fresh-process reopen when the user grants publication rights. Granting those rights must be possible through the no-UI host integration; the product must not require opening the editor just to authorize a save. The current explicit host's default no-save capability is an implementation limit, not a permanent restriction of this workflow.

No editor window does not mean no renderer. Inspection and ordinary authoring can remain without UI, simulation can run headlessly, and a visual check uses a separate real rendered job with its required display/backend capabilities. Saved results reopen normally; unsaved results remain recoverable session state and are not implicitly published to project files.

#### Git-backed project memory

**Every newly created game project owns a local Git repository and versioned project documentation and development journal.** The repository is the durable, provider-independent record of the project's intent, decisions and work; an executor's conversation or private memory is not its sole context store. This is a tooling/project contract shared by editor and no-UI creation. Git and agent dependencies remain outside `Electron2D.dll` and shipped games. No remote hosting account or network connection is required to create a project.

Creation initializes a repository rooted at the new project directory, seeds the context files below from actual template facts and user-supplied intent, and creates appropriate ignore rules before reporting success. Unknown design requirements stay explicit rather than being invented. Missing Git capability or failed initialization is an explicit failure, never a successful project with an unnoticed missing repository. Recovery removes only newly created, operation-owned staging data; existing user files/repositories remain intact. Creating inside an enclosing repository must not silently attach the game to that repository or introduce a nested repository without an explicit project-creation choice.

Opening an existing project uses its actual repository/worktree, including a Git directory represented by a `.git` file. Opening does not reinitialize Git, replace history or silently migrate a project without Git; adoption is an explicit operation. Context identifies repository/worktree root, branch or detached state, HEAD or unborn state, index/worktree changes and applicable live revisions. Another branch's or worktree's notes must not be presented as current verified state.

The initial layout below belongs **inside each created game project**, not the engine checkout. Use ordinary UTF-8 Markdown with repository-relative links and stable entry/decision identities:

| Project path | Owned context |
| --- | --- |
| `AGENTS.md` | Canonical portable instructions: project map, working commands, engineering discipline, Git/journal rules and authoritative document links. Keep essential rules inline and reference longer documents. |
| `docs/project.md` | Game goals, gameplay/scope, constraints, project structure and the supported build/run/check workflow. |
| `docs/decisions.md` | Accepted project decisions and rationale; distinguish current decisions from superseded proposals. |
| `docs/development/index.md` | Current state, active work, known gaps, next steps and relevant journal/evidence links. Maintain a summary rather than a second complete history. |
| `docs/development/YYYY-MM-DD/<entry-id>.md` | One durable record per meaningful human/agent work block. Stable separate entry files avoid a shared append target; corrections reference earlier entries instead of silently rewriting their evidence. |

Journal records follow the [structured work-block contract](#structured-development-journal) below. Link affected files, decisions and evidence using commit/blob identities when committed, or document revisions/content identities when dirty. Update the current summary when state changes materially. Exclude credentials, capability tokens, raw private conversations and generated build/capture bulk; retain useful evidence references and verification limits.

Documentation and journal documents participate in the same session ownership, revision/conflict, recovery and explicit-publication rules as other authoring documents. Human/agent updates must not overwrite open Markdown buffers. The host records confirmed operation/job facts; the agent or human supplies intent and rationale. Record meaningful task/checkpoint boundaries rather than every tool call or keystroke. Interrupted work retains an unfinished checkpoint where available; failed or missing journal publication remains visible and cannot be called durable context merely because code changed. Publication follows the task's granted rights in both owner modes.

On every new or resumed agent connection, including a provider change, expose a compact context entry through shared operations: instruction/document versions, current summary and decision references, relevant journal entries, Git state, and live unsaved overlays/conflicts. The editor adapter supplies it to the executor; external clients discover and read the same content without provider-specific hooks. Retrieve more history on demand. Do not assume every client automatically honors `AGENTS.md`. A fresh client must reconstruct the work from project-owned files and current observations without a previous chat, global personal memory or proprietary memory service. Model compliance and result quality still require measured qualification.

Keep live operations, file publication and Git commits distinct. A commit records selected persisted content; it does not save buffers, replace undo or prove a test used those contents. Shared programmatic status/diff/history and authorized local commit operations check the observed repository/index/HEAD and a bounded path/content set. Preserve unrelated staged/unstaged work; no blanket staging, implicit stash/reset or history rewrite. Initial/subsequent commits follow project policy and real author identity; creation does not invent identity or mandate a commit per edit. Remote creation, push and history rewriting require their own authorization. Branch changes reconcile or reject dirty live documents before changing their base; external Git changes invalidate stale context and use ordinary reconciliation.

This is the **first next project-authoring extension of stage 4**, before general context/composition expansion or provider-independent continuation claims. Extend the existing creator and document owner; do not wait for a complete editor, importer/exporter or runtime API census. Git project initialization and Markdown/journal/Git operations are not implemented by the current bounded workflow.

#### Git workspace in the editor and operation host

**Git is an explicit editor capability.** A repository/worktree view shows the current branch/HEAD, changed and staged files, diffs, history, upstream/ahead/behind state, remotes, worktrees and in-progress operations. The user can perform the operations below inside the editor without asking an agent or opening an external Git application. Agents and no-UI clients use the same typed operations and diagnostics. A terminal button, `.gitignore` or instructions to invoke Git do not implement this contract. Reuse installed Git and its normal repository formats, configuration, hooks and credential helpers; keep Git outside the runtime and game publish.

| Capability | Required behavior |
| --- | --- |
| Repository and review | Create/adopt/open or explicitly clone; inspect status, staged/unstaged/untracked files, bounded text/binary diffs, commit/file history and blame. Show ignored files on request. |
| Index and commits | Stage/unstage selected files and supported text hunks, preview the exact index change, create validated conventional commits and show hook/signing/identity failures. Binary content has an explicit whole-file path. Never commit unrelated staged content accidentally. |
| Branches and integration | List/create/switch/rename/delete local branches; show branches occupied by another worktree. Merge with an explicit strategy; expose conflicts and continue/abort state. Revert/cherry-pick and explicitly authorized rebase/history rewrite retain their real Git semantics. |
| Remotes | Inspect/configure remotes and upstreams, fetch, pull with an explicit integration strategy, and push the selected ref to the selected remote. Show the outgoing commit/ref scope and actual result; pushing is separately authorized, not a side effect of Save/commit. Force push and remote deletion need their own authorized scope. |
| Worktrees | List/create/open/remove linked worktrees and expose lock/unlock, repair/prune where applicable. Respect checked-out branch restrictions and preserve dirty, locked, missing/offline or externally owned trees; removal/pruning is never implicit cleanup of user work. |
| Recovery and advanced work | Inspect/apply/create/drop an explicit stash; resolve text conflicts through shared documents and expose binary/unsupported cases. Destructive restore/reset/clean needs a bounded reviewed target and authorization. Unsupported capabilities such as an unimplemented submodule/LFS profile report their limit, never fake success. |

Authoring ownership is per canonical project worktree, with a separate live session and dirty overlays for each open worktree. Linked worktrees share repository objects/refs while keeping their own HEAD/index. Git mutations coordinate the shared repository as well as the selected worktree; do not equate independent document owners with permission to race on shared refs. Observe Git's locks and recheck expected HEAD/index/ref identities before mutation; external Git actions invalidate stale previews/context. Worktree selection, instruction/journal state and jobs remain bound to their actual root and revision. Worktrees do not imply a concurrent-agent scheduler.

Before a branch switch, merge, pull, stash application or other worktree-changing operation, reconcile or reject affected dirty buffers through the owner. Do not silently save, discard or auto-stash them. Conflict resolution edits the shared document and marks resolution only after explicit publication/staging; abort reports any effects and cannot restore an old snapshot over newer human work. Long/network Git processes report progress, cancellation and terminal results without holding the owner thread. A timeout or cancellation does not prove a push was undone: inspect the remote ref before retrying an uncertain result. Credentials/tokens never enter journal/context; authorization comes from the user's task and grants, not instruction text.

#### Portable project instructions and engineering discipline

The game project's root **`AGENTS.md` is the single canonical instruction source**. Use ordinary UTF-8 Markdown, clear headings and concise actionable bullets; no required vendor frontmatter, personal paths, private extensions or provider account. The product target is fewer than 200 lines for the root entry, not a claim that providers share a size limit. Keep detailed decisions, API reference and work history in linked project documents; load those when relevant. References alone do not guarantee that a client reads their content.

The creator seeds these sections from the actual project template and supported tool profile, then maintains them with the project:

1. Project purpose, directory map and authoritative documents. Unknown game requirements stay explicit.
2. Exact supported setup/build/run/check commands, working directories and prerequisites; distinguish persisted-file commands from live unsaved snapshot operations. Verify generated commands before advertising them; identify unavailable capabilities rather than shipping invented commands.
3. The engineering rules below, including complete scope and meaningful verification.
4. Git safety and Conventional Commits 1.0.0, journal structure/location and completion criteria. Put these essential obligations in the entry itself, with links for detail.

Every executor receives the same engineering policy:

- Read the affected code and callers first; include consumers, tests, fixtures, configuration, exports and documentation in the scope. Complete the requested behavior and its affected contracts while preserving unrelated work.
- Implement the smallest complete solution within existing architecture. Prefer an existing project component/helper, then standard library/platform facilities, then an installed dependency. Justify a new dependency only when needed.
- Keep existing interfaces, layers and useful data forms. Avoid speculative abstractions, wrappers, conversions, configuration, options and future scaffolding. Prefer clear direct code and deletion where they fully solve the task.
- Preserve boundary validation, error handling, data safety, security, accessibility and resource ownership. Fix a common cause in its shared implementation. Brevity cannot justify dropping required behavior.
- Verify non-trivial behavior with a small meaningful check and relevant failure cases. Skip implementation-mirroring tests and tests for trivial reversible edits; retain required project gates. Report only checks actually run and their practical limits.
- Explain non-obvious reasons in comments. A deliberate temporary compromise uses `shortcut: <known limit>, <concrete upgrade trigger>` and cannot defer the requested behavior. Finish with a clear result, evidence and remaining work.

Nested `AGENTS.md` files may add genuinely local guidance. Keep scopes explicit and avoid contradicting shared rules: loader discovery, precedence and overrides differ by client. Preserve existing user instructions; report conflicts or disabled/overridden loading rather than silently replacing files or claiming the canonical policy is active.

Instruction loading belongs to a **qualified client/executor profile**, not to the model provider's name. Official documentation reviewed on 2026-10-26 gives these integration choices; this table is research, not qualification of those clients in Electron2D:

| Client | Canonical-file integration and qualification concern |
| --- | --- |
| OpenAI Codex | Native root-to-working-directory `AGENTS.md` discovery. Account for more-specific instructions, `AGENTS.override.md`, configured fallback names and the combined instruction-byte budget; verify actual loaded sources in a fresh session. |
| Anthropic Claude Code | Current versions support native `AGENTS.md`, subject to version, project-instruction settings and competing `CLAUDE.md`/local files. Where the profile requires it, a minimal `CLAUDE.md` imports `@AGENTS.md` as an actual import line. Check loaded instructions instead of assuming either universal native support or a universally required wrapper. |
| Google Gemini CLI | Configure project instruction discovery with `context.fileName` set to `AGENTS.md`, or use a minimal `GEMINI.md` importing `@./AGENTS.md`. Verify loaded memory; avoid configuring both paths to load the same rules twice. |
| Cursor | Native root and nested `AGENTS.md` support. Keep essential instructions in the file; a linked document is not automatically inlined. Specialized client rules are optional additions, not a second policy copy. |
| GitHub Copilot | Native support varies by feature/client. Use `AGENTS.md` where supported; other surfaces use `.github/copilot-instructions.md`. A plain Markdown pointer is not a guaranteed import: the integration must supply the resolved canonical content or declare this profile unsupported. |
| Other executors | Use their documented native loader, a supported import, or adapter-supplied canonical text. No automatic-discovery claim without an exercised profile. |

Create a minimal provider entry only when the chosen profile needs it; do not prepopulate parallel policy copies or modify global user settings. Resolve supported imports inside the project, preserving existing files and detecting duplicates/conflicts. An adapter may supply resolved canonical content when its executor lacks a loader. Bootstrap identifies applicable instruction paths, versions/content identities and scope, and distinguishes native loading from adapter delivery. Verify effective receipt using client diagnostics where available and an exercised task; missing, overridden or truncated context remains visible. Refresh instructions on resume/reconnect or invalidate their receipt after a relevant edit. Project text remains context, not enforcement: session permissions, validation, Git and journal checks enforce their own operation contracts. Arbitrary external agents cannot be guaranteed to comply merely by having this file.

#### Bounded context and documentation workflow

**A new task must not preload the documentation tree.** Bootstrap carries the applicable compact instructions, current objective/state summary, worktree/HEAD/live revisions, active skill metadata and references to relevant contracts/evidence. Read an index first, then the needed sections, then implementation/evidence only when it changes the next decision. Do not recursively inline all linked pages, skill references, API declarations, Git history, journal entries or logs. A provider import may load content eagerly, so imported text counts toward the initial budget.

The first implementation uses a default **16 KiB UTF-8 budget for engine-supplied bootstrap text**, counting duplicate/imported instructions and an activated skill entry when supplied. Generated game `AGENTS.md` targets at most 8 KiB as well as fewer than 200 lines; the shared skill entry targets at most 4 KiB. These are product budgets, not vendor context/token limits. Reserve the remaining budget for task/state routing, reduce it for a smaller known client allowance and report bytes plus tokens when a reliable counter exists. Native/global instructions outside engine control remain separately identified; do not promise a bound on an arbitrary external client's whole context. If essential instructions cannot fit, report the conflict and narrow/split them rather than silently truncating required rules. Expose budget/loaded-source diagnostics in the editor and bootstrap result.

Shared documentation/context operations provide a bounded path/heading index, filtered search with snippets, section/range reads and journal summaries. New read responses default to at most 16 KiB of serialized content with explicit limits, omitted counts and continuation cursors where more exists. References carry path/anchor, scope, source revision/content identity and query where relevant; invalidate stale cursors after edits. Avoid resending unchanged documents/schemas; refresh relevant changed content by identity. Large documents, diffs and job logs remain retrievable artifacts instead of being injected wholesale. Discover only the needed operation schemas. Ordinary file search/range reads remain a fallback where no richer index is implemented; a vector database is not a prerequisite.

The same discipline applies to authoring and maintaining documentation:

- Read the owning requirement/decision and affected current-state sections before changing behavior. Follow only dependencies needed for the task; a cross-link is not an instruction to read the whole graph.
- Keep each fact/contract in one canonical place with stable headings/IDs, useful titles, scope and current status. Route summaries to it. Split growing documents into bounded topics and update the index/links; 500 lines is an upper bound for a decision document, not a target length.
- Update affected instructions, commands, current-state pages, decisions and evidence links with the change. Record proposals as proposals, planned capabilities as planned and verification limits explicitly. Update an active decision in place when it changes; preserve rationale/supersession and factual journal corrections. A journal records work and reasons; maintained documentation explains the current product.
- Keep the current-state index small: objective, verified state, unresolved constraints, next action and selected journal/decision references. On resume or provider/worktree change, recheck HEAD, instructions, dirty revisions, rights and stale evidence instead of trusting an old summary. A compaction checkpoint preserves those identities and unfinished actions, not the whole conversation.

Measure initial context size, retrieved bytes/tokens, relevant-source coverage and task completion on projects with growing documentation/history. Mandatory context must fit without requiring the agent to summarize an already overflowing prompt. Correctness and needed contracts take precedence over minimizing bytes; the remedy is relevant staged retrieval, not omitting required instructions.

#### Bundled development skill and provider support

The **editor/tooling distribution must include a provider-neutral `electron2d-development` skill** with the same versioned source for every qualified profile. It teaches operation discovery and editor/no-UI owner attachment, unsaved revisions/conflicts/history, snapshot build/run/evidence, project Git, the documentation workflow and the six-section journal. It carries the shared engineering policy by reference to applicable project instructions. Runtime-only packages and shipped games do not acquire agent dependencies. Source instructions alone do not establish a delivered or installed skill.

Use the open Agent Skills format: `electron2d-development/SKILL.md` with portable YAML `name`/`description` and a short Markdown workflow, plus focused relative references for authoring/verification, project context/documentation/journal and Git. Load only metadata for discovery; the entry on activation; one relevant reference when needed. Do not copy the engine manual or inject all references through `AGENTS.md`. Add scripts/templates only for a real repeated operation and verify them against the shipped tool version. Do not embed provider-specific command substitutions, assumed tool names, blanket tool permissions or a mandatory private extension in the shared entry.

Package the canonical directory under the editor's `skills/` payload with engine/skill/protocol versions and content identities. Project setup offers a project-local installation under `.agents/skills/electron2d-development/` where the selected client supports it; use the client's documented directory/adapter for other profiles, such as `.claude/skills/`. Provider metadata/import wrappers are generated from the same canonical package, not independently maintained policies. Detect duplicate names, unavailable discovery, wrong versions and modified installations; preserve user files and upgrade only recognized owned content. Do not silently install globally. Verify loading and the required references from the actual installed artifact in a fresh client, including a clone/worktree and offline retrieval of bundled instructions. Model execution can still require the user's provider login/network.

The explicit model-provider targets are **OpenAI, Anthropic, Google, DeepSeek, Moonshot AI/Kimi, Alibaba/Qwen, Z.ai/GLM and MiniMax** through qualified editor-controlled executor profiles. **GitHub Copilot CLI and Cursor Agent** are additional external-client targets for shared operations and the skill. Prefer native **Kimi Code CLI** and **Qwen Code** profiles for their respective providers; use a compatible existing executor for provider backends where appropriate. This does not promise an editor-control protocol for every external application or support every model/endpoint exposed by those applications. Keep current support in the [provider/client matrix](../components/project-agent.md#provider-and-client-support), and list the same names and qualified/planned status in every root README locale and documentation entry. No catch-all “all providers supported” label.

Keep **executor identity and model-provider identity separate**. The editor's agent setup selects and displays both identities and the active endpoint/model profile. A reusable Codex, Claude Code or other compatible executor can run a different vendor's model without making that vendor OpenAI or Anthropic. Official DeepSeek, Z.ai and MiniMax documentation describes such integration routes; Kimi Code CLI and Qwen Code document native ACP, MCP and skill facilities. These are candidates, not proof of Electron2D compatibility. Reuse an executor's agent loop and provider configuration rather than adding a separate loop or runtime dependency for each vendor.

Qualify each provider/backend plus executor combination independently, including API family, endpoint/region or self-hosted origin, exact model/client versions, authentication mode, tools, reasoning/streaming/cancellation, context budgets, skill loading and journal/Git publication. OpenAI- or Anthropic-compatible model APIs do not supply editor control or guarantee identical tool behavior. The existing Codex/OpenAI result does not qualify Codex/DeepSeek, and a cloud Qwen result does not qualify a local Qwen endpoint. Keep credentials outside project files/context; isolate launch configuration per profile and preserve the user's global settings. Provider switches reload durable project context and invalidate stale profile/acceptance assumptions.

Qualification records the provider, client/executor and exact version, OS/transport, selected model, authentication mode, editor control versus external tools, instruction/skill loading, publication/Git rights and actual acceptance evidence. A working skill loader or generic MCP compatibility establishes neither in-editor executor support nor model behavior. Currently only the bounded OpenAI Codex profile is qualified; the other named targets and bundled skill delivery require implementation and acceptance before being advertised as available. No provider is required for manual development or ordinary .NET game builds.

#### Conventional project commits

All newly created project commits use [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/): a type, optional parenthesized scope, optional breaking marker, colon, space and description; optional body and footers follow blank lines. For example, `feat(player): add jump buffering`, `fix(save): preserve the previous slot` and `docs: record level constraints`. Use `feat` for new functionality and `fix` for a correction. Project policy also permits suitable types such as `docs`, `refactor`, `test`, `perf`, `build`, `ci` and `chore`; the specification does not mandate a closed type list.

An authorized breaking change uses **either** `!` before the colon **or** the uppercase `BREAKING CHANGE:` footer (the specification also accepts `BREAKING-CHANGE:`). The marker does not authorize breaking an accepted contract or automatically publish a release. Commit a coherent verified task/checkpoint, not each tool call. A failed commit leaves the task's actual persisted/uncommitted state explicit; never invent author identity or rewrite old messages to make existing history conform.

The shared commit operation validates the new message before mutating the index/history and checks the bounded persisted selection and observed Git state. Reuse project hook/CI validation where present; instructions alone do not establish enforcement, and direct Git access outside the host retains the executor's ordinary permissions. UI and no-UI clients have the same policy. Preserve the earlier separation between Save, live history and commits, unrelated staged changes, and separately authorized remote/destructive actions.

#### Structured development journal

Record **meaningful work blocks**, not prompts, turns or raw tool output. Group investigation, failed candidates, the final change and its verification for one objective in one entry; split independent objectives. An acknowledgement or trivial answer does not create an empty entry. Use the project's language and ordinary Markdown. Each entry has a stable ID, concrete title, observed date/time with timezone where known, actor/task attribution and optional artifact/correction references. A provider-private conversation identifier may be extra attribution, never the required key.

All six sections are required. Their semantic identities are stable; human-readable headings may follow the project's language. When a section has no applicable facts, say so briefly rather than inventing content.

| Section | Required content |
| --- | --- |
| Context | User objective, starting state, scope and constraints in the author's own words. Enough to continue without the conversation. |
| Timeline | Significant observed phases, useful failed candidates and reasons for rejection. Record actual times with timezone/date across midnight; mark unknown time explicitly. |
| Changes | Final behavior and affected files/components. Distinguish abandoned/reverted experiments and pre-existing or unresolved defects. |
| Decisions | Choices, evidence, rejected alternatives and causal reasons. |
| Checks | Exact executed commands, statuses, relevant counts, input revisions/hashes and artifact references; failures, partial results and verification limits. Planned checks are not results; compilation is not rendered or human acceptance. |
| Next steps | Remaining work, smallest useful continuation and any required user decision; explicitly say when none remains. |

Summarize the relevant Git baseline once and the actual delta, adding a commit identity only when one exists. Preserve full digests when they identify evidence. A journal entry may precede a commit; identify dirty/live input honestly. Do not require an entry to contain the hash of the commit that contains that same entry: resolve that association from Git by entry ID/path, avoiding a self-referential follow-up commit loop. Link project-relative artifacts and decisions, not raw private conversations or secrets.

The human or agent authors intent and rationale; the host validates required sections and attaches confirmed operation/job/publication facts without pretending to infer motivation. Publish through shared Markdown operations with expected revisions and granted rights. Completion reports distinguish a durable entry from a recoverable draft or failed write. Retry an uncertain write using the same entry ID without duplication; a later correction gets a new ID referencing the earlier entry, while an independent later block does not supersede it. Do not rewrite evidence silently. A missing/failed publication requires repair or an explicit reported limit before claiming that the task's context is durable. The current-state index links the material result and smallest next step without duplicating the whole history.

#### Session ownership and concurrent authoring

- One authoritative owner admits mutations for a project root. With an open editor, external operation clients attach to its session. Without an editor, an operation host can own the same session core. Discovery, owner lease, authentication, expiry and crash recovery must prevent two independent writers; an unreachable or ambiguous live owner must not silently cause a writable headless fallback.
- The session owns open documents, unsaved scene/resource/code state, stable document/object identities, selection context, persistence state, diagnostics and operation history. Reuse the accepted typed archive and public runtime capabilities; this decision does not select a replacement file format. File paths and node names alone cannot identify objects across rename/reparent operations.
- Human and agent changes are serialized through the session's owner thread. Network/model work and build/game processes cannot hold that thread while waiting. Inspecting a scene or editing its authored data must not implicitly activate gameplay callbacks.
- Mutations name their origin and expected document/object revision. Validate a bounded change group before applying it, publish its changes as one committed operation and return the resulting revisions. Reject stale overlapping edits with useful conflict information. A stale whole-document replacement must never overwrite a newer manual buffer. Unrelated editing can continue while the agent reasons or a job executes.
- Revision identities remain monotonic across undo/redo; the cursor-like `UndoRedo.Version` is not a concurrency token. Use [ADR 0105](undo-history.md#adr-0105) for the reusable history mechanism. Its callbacks are not automatic transactions: the session must establish its own validation, recovery and partial-failure boundaries before promising all-or-nothing authoring. Saving multiple files also needs an explicit recoverable publication contract; atomic replacement of one file does not establish group atomicity.
- An agent change group participates in the editor's normal history. Selective undo checks affected state against later human edits and reports a conflict when necessary; it cannot restore an old snapshot over unrelated or overlapping manual work. Cancellation stops pending work at a defined commit boundary and reports any already committed effects.
- Unsaved changes are visible to session clients and become dirty documents. Applying them does not implicitly save a human's buffers. External disk changes are reconciled against the persisted base and live revisions; clean documents can refresh, independent edits can merge when supported, and unresolved overlaps remain explicit conflicts. A file watcher is an ingress for these changes, not the session's authority.
- Committed authoring changes notify scene tree, inspector, resource/code views and viewport in the next editor dispatch cycle without a save/reopen cycle. Preserve unaffected selection and editor state. Immediate document/UI updates do not imply live CLR code replacement: [ADR 0091](scripting.md#adr-0091) initially uses build and restart; hot reload and state migration require their own executable contract.

#### Agent control and engine tools

There are two distinct integration boundaries:

| Boundary | Responsibility |
| --- | --- |
| Editor to agent executor | Start/resume a conversation, supply task/selection context, stream activity, handle user input and permission requests, interrupt work and retire the process/session. ACP is the preferred initial protocol candidate; a provider-specific adapter can map an executor's supported contract. |
| Agent to Electron2D operations | Discover and invoke typed project/scene/resource/code operations, query current state and diagnostics, submit jobs and retrieve results/artifacts. MCP is the interoperable tool boundary; local UI clients invoke the same operations without a transport round trip. |

ACP and MCP are complementary, not alternative implementations of project semantics. Negotiate capabilities and pin exercised protocol/executor versions. Neither protocol supplies scene revisions, conflict handling, undo or a security sandbox. The first actual integration must verify its authentication, buffer access, cancellation, failure and cleanup behavior; a manifest, fake executor or launched terminal alone is insufficient.

The editor owns its agent panel: task input, attached selection/context, conversation history, operation/change timeline, job progress, relevant diagnostics/images, interruption and safe undo. The executor can run in a separate local process while this panel is the user's complete interaction surface. Model calls, credentials, provider packages and agent lifecycle stay outside `Electron2D.dll`. Reuse a suitable executor's agent loop behind the adapter rather than binding the project model to one provider or constructing a general-purpose orchestration framework first.

Expose clear semantic tools backed by operation-specific typed models. Discover the full applicable operation surface progressively, with a compact active set, scoped search/inspection, bounded responses and actionable errors. Include names and relevant context alongside stable identities. Tool descriptions document prerequisites, effects and failure behavior; publish only executable capabilities, without successful placeholders. Transport field names do not authorize arbitrary runtime `Get/Set/Call`.

Context must identify the target project/owner, documents and stable objects, together with the observed revisions. A user's selection is useful context, not permission to modify everything nearby. For spatial tasks, combine scoped structured objects, viewport bounds and coordinate-space information with an image when useful. Identify an authored preview separately from rendered game evidence, and retain the image's source/revision or snapshot identity. Fetch detailed context as needed rather than injecting the complete scene, code and tool catalog into every turn. The panel makes affected objects and owner-confirmed operations visible while work proceeds.

Agents must be able to compose supported typed operations to perform repetitive or novel tasks without a model round trip for every object. Composition remains a client/executor capability over the same session boundary: every mutation retains validation, permissions, expected revisions, attribution, history and cancellation semantics. A sequence of committed groups is not automatically one atomic transaction. This does not select a new script interpreter, arbitrary runtime dispatch, a provider-specific code mode or a replacement scenario SDK. Evaluate a concrete composition mechanism against real tasks after the first integrated workflow; reuse an executor's suitable facilities where possible.

Start with one agent alongside the human. Permissions cover authorized task scope; routine reversible changes need not prompt for every call. Destructive/external effects follow explicit policy and remain attributable. Source code, tool output and imported assets are data, not authority to expand permissions. Direct agent/shell file writes cannot bypass unsaved-buffer conflict checks: route them through the session or reconcile them as external edits. Concurrent multi-agent mutation, remote collaboration and automatic conflict resolution require measured need and separate verified capabilities.

#### Snapshot jobs and observable results

Build, test, run and export jobs consume an immutable input snapshot that includes the applicable source/resource/settings closure and unsaved document/code overlays. Materializing it in temporary storage must not mark project buffers saved or advance their persisted revisions. A job must not silently test older disk content while the editor displays newer input.

Each job identifies its input snapshot, document/content revisions, build configuration and engine/project identities. Results and artifacts retain that identity and become visibly stale when relevant current inputs differ. A running job does not block further authoring. Job status distinguishes queued, running, cancelled, failed and completed; enqueue or process start is not successful verification. Deadline/cancellation and owned-process cleanup include inherited workers and failure recovery.

The job layer uses public scheduling, input, persistence and capture capabilities with the modes below. It is shared by editor and no-UI hosts; it does not preserve the old compiled batch API or introduce another game loop.

#### Three distinct execution modes

| Mode | Required services and behavior | Verification output |
| --- | --- | --- |
| Authoring without editor UI | Project/scene/resource operations, serializers, import/build tools; scene data can be edited without activating gameplay callbacks or opening editor windows | Changed files, validation/build diagnostics and operation results |
| Headless simulation | Real scene lifecycle, input state/routing, fixed/process steps and applicable simulation services; no window or renderer is required | State observations, events, scenario assertions and exit status |
| Rendered batch | Applicable simulation plus an actual selected renderer, explicitly configured target dimensions and capture timing | Images or recordings, backend/capability identity and scenario results |

Headless simulation must not claim visual verification or return a fake successful capture. A hidden native window, software fallback and a GPU offscreen target are different capabilities. Rendered batch must use the actual renderer and preserve its documented precision/capability limits; independent offscreen targets require their own complete lifecycle, sampling and readback slice. Unsupported requests fail explicitly.

The editor process selects the transient Engine.IsEditorHint authoring role before scene construction. Snapshot game/scenario jobs remain separate processes with the default runtime role; launching from the editor does not make them authoring sessions. This role suppresses built-in autoplay while preserving explicit preview and ordinary lifecycle, as owned by [ADR 0015](core-object-runtime.md#adr-0015).

#### Runtime and scenario contract

- Batch execution shares ordinary lifecycle semantics: ownership, activation/Ready ordering, process/physics ordering, pause/time-scale policy, deferred work, input edges, exceptions, quit and teardown. It must not approximate these with a second game loop or enable a hidden owner thread. GUI/Window-dependent operations require an explicit headless viewport/host capability rather than assuming native services exist.
- The host provides an explicit timestep, step/frame budget and stopping conditions. Input is injected through the real state-and-delivery boundary before the specified step. Event-only viewport delivery is not equivalent to committing global Input state.
- Batch jobs define deadline/cancellation and isolate game execution so a non-returning user callback cannot indefinitely block the authoring frontend. The tooling host owns process/job control; this does not add a hidden game thread or change runtime callback semantics.
- Repeatability claims name the engine/build revision, project/resources, scenario, random seed, timestep, platform and backend. Fixed stepping does not by itself promise bit-identical results across platforms, native libraries or renderers.
- Each run returns an explicit result and meaningful exit code. The first tooling slice defines versioned structured diagnostics, a separate log channel, observations/assertions and artifact references; callback failure, exhausted execution budget or missing capability cannot produce a successful result. Application console output must not corrupt the machine-readable result.
- Capture has a defined frame/step and completion boundary and uses public runtime capabilities. Internal test readback does not establish a consumer-facing capture API. Debug observations are opt-in; reporting, serialization and transport stay outside measured engine hot paths unless allocation budgets are independently proven.

#### Typed files, diagnostics and discoverability

- Agent-native design preserves the full applicable API, strictly 2D scope, one-runtime-assembly boundary and typed C# adaptations. It does not authorize narrowing the contract, inert aliases, `Variant`, general `object`/`dynamic` payloads or string-based runtime `Get/Set/Call`.
- Project/scene/resource files must be inspectable and versioned, produce stable focused diffs, and preserve type identity, hierarchy, ownership, typed stored properties, node/resource references and shared resource identity. The concrete format, codecs, type/factory registration and migration rules are specified in the first serializer slice under ADR 0023. ADR 0013 now selects the first binary typed archive version; its public typed metadata/state inspection and explicit schema document are available. Textual authoring/diff export remains a separate tooling capability.
- CLI and UI use the same serializer/loader. File writes must avoid losing the previous saved data on failure; recovery and validation boundaries are tested. This does not change the existing clear-on-attempt `PackedScene.Pack` contract. A saved result must load correctly in a fresh process rather than relying on in-memory factories or caches.
- Structured transport/file values map to operation-specific typed models and approved property codecs. Their serialized field names do not create an untyped runtime value or arbitrary member invocation boundary.
- API discovery and documentation must provide compact, version-matched access to signatures, defaults, units, coordinate spaces, lifecycle/ownership, ordering, errors, executable examples and backend limits. Generated declarations and coverage states remain distinct from semantic verification; unknown/unverified behavior must not appear as supported.
- Diagnostics identify the operation and affected project file, scene/node/resource, source location or backend stage where available. Stable diagnostic identities and structured fields accompany readable messages. Inspection and evidence must remain useful to both the agent and the human reviewer.

### Delivery and acceptance

Implement connected executable slices under the [maintenance contract](../maintaining.md). Start the session foundation with the next project-authoring slice, before project management, scene inspector or code editing acquires a private UI-only document model. Existing persistence, history, scheduling and capture are sufficient foundations to begin; completion of the entire API census, renderer feature backlog or all-platform matrix is not an entry gate. Missing capabilities needed by the selected slice still enter their owning runtime domains first.

| Stage and entry point | Deliverable and exit evidence |
| --- | --- |
| 1. Next project-authoring slice, before a functional editor project workflow | A no-UI session core with one owner, stable identities, unsaved scene/code documents, bounded typed operations, revisions, events, persistence/recovery and grouped history. Real tests cover independent owner processes, two operation clients, stale/conflicting edits, undo after manual work, external changes, failed apply/save and fresh-process reopen. No agent/model connection is needed to establish these deterministic guarantees. |
| 2. First functional editor project workflow, using stage 1 | Minimal open project, scene tree/inspector/code views and preview subscribe to the shared session; manual and programmatic changes appear together without forced save. Snapshot jobs exercise an unsaved edit, build, fresh game execution, actual capture, stale results, deadline/cancel and cleanup. Replace/remove the existing Batch controller/SDK/formats and affected consumers/docs in this job slice, without a compatibility bridge. Runtime entry points retain their separate owning contracts. |
| 3. First agent-enabled editor milestone, after stages 1–2 and before editor polish | A real local operations transport and one real agent adapter, preferably ACP where supported, connected to the editor's task/conversation panel. Verify selection context, unsaved reads/writes, meaningful progress, interruption, disconnect/reconnect, missing capability and executor failure. Run the co-development acceptance scenario below with the stated executor/model/tool versions; a fake adapter remains only a deterministic test fixture. |
| 4a. First extension after co-development | Git-backed creation, shared Markdown/six-section journal publication, validated conventional commits and bounded indexed context in both owner modes. Supply the canonical development skill with the qualified editor/tooling artifact and verify its actual installation/loading plus fresh-client continuation. |
| 4b. Git workspace, using 4a's repository/document boundary | Editor and no-UI Git operations for review/index/commits, branches, remotes/fetch/pull/push, worktrees and integration/conflict/recovery. Extend shared documents as required; verify dirty-buffer protection, shared-ref coordination and failed/uncertain external effects. |
| 4c. Provider and capability expansion, after their required operations exist | Qualify the named provider/backend plus executor profiles in the support matrix, including Kimi Code CLI, Qwen Code and reused executors for DeepSeek/GLM/MiniMax; qualify Copilot CLI and Cursor external clients with the same skill/context/journal contract. Expand semantic tools, spatial context and composition, measuring repair quality and regressions. Qualify installed distribution, additional platforms and larger workloads. Parallel agents/hot reload retain separate justified slices. |

The first bounded implementation target is one existing typed scene and one C# source buffer: open/inspect them, change an Entity transform through typed session operations, preserve an unsaved manual edit, reject an overlapping stale edit, undo safely, then save/reopen in a fresh process. Establish actual owner exclusion across processes. This proves stage 1's document/operation boundary before building a full project manager, plugin framework, language service or agent transport.

The minimum co-development acceptance scenario opens a real project, makes a human edit without saving, asks the agent from inside the editor to change another part, and shows both in the normal views. An overlapping stale edit must conflict without data loss. Undo/cancellation preserves later manual work. Build/run verifies the intended unsaved snapshot, returns state assertions and actual rendered evidence, and marks older evidence stale after another edit. Include invalid input, callback/build/runtime failure, process disconnect, recovery and cleanup. Repeat the shared operation path without editor UI. This scenario, not terminal launch or panel screenshots, establishes the first integrated capability.

Expanded-context acceptance must distinguish two open projects and renamed/reparented objects, keep selection context separate from edit scope, and identify stale images and coordinate spaces. A composition slice must exercise multiple typed edits, a stale intermediate revision, cancellation after a committed group and safe undo after human work. Test the real external client against both owner modes, including explicit no-UI publication rights, save and fresh-process reopen, before claiming that complete user workflow; transport tests alone establish only its underlying tools path.

Git/context acceptance creates a project through UI and no-UI operations, verifies its dedicated repository and seed documents, and exercises unavailable Git, initialization failure and existing/enclosing repository preservation. Perform an edit plus an attributed journal update, publish selected files, commit only authorized content, then reopen/clone and reconstruct work from a fresh independent client without the prior conversation. Reconnect before saving to verify dirty overlays; test denied publication, interrupted journal writes, concurrent Markdown edits, unrelated staged files, unborn/detached/changed HEAD and external checkout conflicts. Journal claims must match actual checks; private tokens/generated bulk stay absent. Qualify real executor/provider switches separately from these deterministic document/Git checks.

Instruction/journal acceptance verifies actual generated commands, root/subdirectory discovery and a fresh/resumed client with the canonical file or its required import/adapter path. Exercise competing instructions, missing/truncated context and instruction edits; inspect effective loading and record the client/version/settings used. Check six journal sections, unknown-time handling, failed/retried publication without duplicate entries and a referenced correction. Commit acceptance covers optional scopes/bodies/footers, both breaking-marker forms and rejection of malformed messages before index/history mutation. A real task must also establish the shared engineering policy and fresh-provider continuation; schema/message checks alone cannot prove agent behavior.

Context/skill acceptance uses a project with large documentation and journal history: a fresh task receives only bounded bootstrap/routing, then retrieves a relevant contract and selected evidence without loading the whole tree. Check multibyte UTF-8 budgets, imports/duplicates, missing essential instructions, paging/stale cursors and resume after edits. From the actual editor/tooling package, verify skill metadata, references, version/content identity, project-local install/upgrade preservation, discovery/activation and a real authoring plus documentation/journal task for each claimed client. Schema checks are not skill behavior acceptance.

Git-workspace acceptance exercises the editor UI and shared no-UI operations against real local repositories and a disposable local bare remote: branches/worktrees, partial staging, unrelated staged content, commit hooks, fetch/pull/push, rejected/non-fast-forward and uncertain pushes, conflicts with continue/abort, external ref changes, cancellation and dirty/locked worktree removal refusal. Explicitly verify that live buffers and another worktree's refs/index are preserved. A local remote does not qualify hosted authentication/network delivery. Update all README locales and the current support matrix only from the exercised provider/artifact evidence.

The [coverage roadmap](../coverage/roadmap.md#live-project-and-agent-delivery) tracks this dependency order without promoting absent editor APIs. Human assessment of game feel and visual quality remains separate from automated correctness.

Measure verified task success, repair iterations, elapsed time, required context, manual interventions, diff size and regressions using stated agent/model/tool versions and fixed tasks. A provider adapter, screenshot, synthetic benchmark or successful build alone does not prove the complete agent-native workflow.

### Current implementation and verification boundary

The [editor project workflow](../components/project-jobs.md) now implements stage 2 for one root binary-SDK .NET project, one typed scene and one C# buffer. Native scene tree/position inspector/source/history/passive preview bind to the shared owner. Version-two immutable jobs freeze unsaved values plus the qualified managed/native SDK, build outside the input, run fresh headless/native processes, validate actual capture/provenance and mark stale results. The old controller, scenario SDK and version-one formats are removed without a compatibility bridge. Linux process groups and an owner-lifetime pipe implement cancellation/deadline/descendant retirement, including abrupt owner death. Other-platform job control requires its own implementation.

Typed archives, ResourceSaver.SaveScene, public history/property descriptors, MainLoop/Engine scheduling and typed Input are runtime foundations. Public Viewport.GetTexture/ViewportTexture.GetImage, independent offscreen targets, RenderingServer.ForceDraw and the movie-writer lifecycle provide native output. Callback-first Engine overloads commit input before the first native step. [Low-processor rendering](../components/low-processor-rendering.md) preserves input/processing while skipping unchanged output; its RGB probe remains distinct from agent acceptance.

The [bounded no-UI project session](../components/project-session.md) now implements stage 1 for one existing typed scene and one C# buffer: an exclusive OS owner lease, stable identities, two local clients, typed groups, monotonic revisions/conflicts, events, guarded history and persistence/recovery. Independent-process exclusion, crash recovery, failed apply/save and fresh-process persistence execute in its public consumer. Native shared views and snapshot jobs now consume this same core. [The bounded agent workflow](../components/project-agent.md) now supplies authenticated Unix ingress, real MCP stdio, a replaceable Codex app-server executor and native task/conversation/control. The qualified profile is Linux, MCP 2025-06-18/2025-11-25 and codex-cli 0.163.0; ACP remains an unimplemented alternative. Real native-panel acceptance uses the actually selected model and verifies unsaved edits, stale conflict repair, capture/assertions, interruption and conversation reconnect. Unsupported interactive forms/approvals are declined/reported; scoped Save/UseDisk rights are selected explicitly before connection. Installed distribution, import/export, general scene text authoring, foreign-platform qualification and measured agent/human acceptance remain separate work. The archived predecessor's workspace models, in-process MCP adapter and panel harness inform the design; they are not imported code or proof of a current live integration.

Missing capabilities remain gaps with exact triggers in [coverage](../coverage/index.md). Platform claims follow ADR 0021; zero-allocation claims follow ADR 0014. Public session/job and native workspace/application tests exercise create/open, unsaved manual/programmatic edits, shared history, exact snapshot builds, fresh-process simulation/capture, stale results, failure and owned cleanup. Documentation/link/decision checks verify this record only; neither establishes improved agent performance or human visual acceptance.

### Consequences

- New runtime and authoring capabilities must be discoverable, executable and observable through the relevant supported tooling path as that path is implemented; absent prerequisites stay explicit.
- Human and agent authoring have one live semantic authority, and user review receives attributed changes plus evidence tied to the input actually exercised.
- Headless and visual verification remain separate capabilities, preserving honest backend and platform reporting.
- The design improves development by human programmers as well as coding agents, while retaining the runtime's typed and performance boundaries.

### Rejected alternatives

- GUI-only authoring requiring an agent to locate and operate widgets for ordinary project/scene changes: it leaves programmatic operation and repeatable validation undefined.
- Separate agent-only engine semantics or a privileged private API: it bypasses the ordinary game contract and permits tools to succeed where consumers cannot.
- Universal dynamic runtime dispatch or a mandatory embedded AI provider: neither is required for compiled typed authoring and both change existing product boundaries.
- Treating no-render execution, compilation or software-only screenshots as proof of GPU/visual behavior: these verify different contracts.
- Publishing placeholder tooling or claiming agent-native completion from this ADR: capability acceptance requires the executable end-to-end workflow above.
- Keeping a second disk/batch authoring authority or preserving the existing tool SDK solely for compatibility: either can diverge from the editor's unsaved project state.
- Starting with a general multi-agent framework, mandatory cloud account or a task board before a real co-development slice: these do not establish the shared authoring contract.

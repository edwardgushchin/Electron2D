# Engine inventory

Last updated: 2026-09-24

This is the exhaustive inventory of implemented Electron2D engine domains, components, and production types. Test-only helpers are not engine types.

Electron2D is 2D-only. Its game runtime targets Windows, macOS, Linux on X11 and Wayland, Android, iOS, and Web; its editor targets Windows, macOS, and Linux on X11 and Wayland under ADR 0021. All currently implemented production rows in this inventory are runtime types belonging to `Electron2D.dll`. Approved managed SDL3-CS bindings are internal source in that assembly under ADR 0012; native libraries remain platform deployment files. The future first-party editor is a separate executable consumer under ADR 0027 and has no implemented production rows yet.

## Explicitly absent

There are currently no production types for packed/exported virtual filesystems, import remapping, resource-UID resolution, platform pipes, public native controller handles, audio, collision/rigid-body physics, general asset loading/saving/import management, scene file loading/saving, scripting, logging, movie writing, an editor application, or networking. Managed `Image` supplies CPU storage/processing, six file/buffer decoders and PNG/JPEG encoding; its raw compressed formats do not imply encoder, decoder, texture, or GPU support, and ADR 0039 defines exact triggers. Managed typed input events, action mapping/state, and SceneTree propagation are implemented; cursor/window control, buffered native input, and mouse/touch emulation are implemented by DisplayServer and Input; physical controller verification, sensors, MIDI, shortcuts and complete GUI/viewport routing remain open under the exact triggers in ADR 0038. The complete implemented engine-owned vector family is `Vector2`, `Vector2i`, `Vector3`, `Vector3i`, `Vector4`, and `Vector4i`; the rectangle family is `Rect2` and `Rect2i` with typed conversions and persistence; `Rect2`, `Transform`, and `Entity` use `Vector2`, and floating rectangle transform operators are implemented. Three-dimensional scene types remain intentionally absent. Reusable `Timer` nodes, lightweight `SceneTreeTimer` delays, and typed `Tween` sequences all use the host-driven frame schedule; none owns a wall clock, background task, or second scheduler. Tween property and callback endpoints are typed delegates rather than serialized paths or callables. ADR 0027 reserves an editor source boundary but does not make an editor project, assembly, type, UI, or self-hosting behavior implemented. ADR 0028 selects the SDL3 GPU API as primary renderer and SDL_Renderer as the baseline fallback. Both execute the documented canvas baseline; shader materials are limited to the tested uniform/texture interface described above. There are also no Android or iOS application hosts, mobile packages, Web browser host/build/storage integration, signing workflows, or complete native/browser target tests; The Linux Wayland example launches and closes through real input; X11 and other target packages remain unverified. `FileAccess`, `DirAccess`, and `ProjectSettings` resolve directory-backed `res://`/`user://`; no archive mount exists, and `uid://`/`pipe://` fail explicitly. FastLZ and Zstandard remain explicit file codec gaps. Linux extended attributes and directory behavior are verified locally; implemented macOS and Windows backends are not native-host verified, no extended-attribute backend is claimed for Android or iOS, and mobile directory links/drive enumeration await host integration. `ConfigFile` itself continues to accept ordinary operating-system paths. `PackedScene` provides only typed in-memory capture/instantiation; it does not add a scene file format, editor inheritance, placeholders, or persistent event endpoints. Selecting `Box2D.NET` does not make physics implemented. `Engine.Start`/`AdvanceFrame` supply externally driven fixed-step callback scheduling. `Engine.Run` additionally owns the monotonic clock and MaxFPS waits and drives the DisplayServer native pump plus RenderingServer submission. Collision simulation and renderer draw-count queries remain absent. The shader build tool imports HLSL, GLSL and compatible SPIR-V; this is not a general resource importer. Persistent event connections remain blocked by the absence of a typed stable endpoint schema. Typed property descriptors exist for storage and future tooling, but no editor UI exists. Node, CanvasItem and the spatial Entity subclass are implemented. All three-dimensional engine functionality is outside the product boundary.

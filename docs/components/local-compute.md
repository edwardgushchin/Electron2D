# Local compute

Last updated: 2026-10-11

The public [RenderingDevice](../classes/RenderingDevice.md) compute slice is created by `RenderingServer.CreateLocalRenderingDevice()` under [ADR 0028](../decisions/rendering.md#adr-0028). It supplies a portable compute path for application algorithms without exposing native handles or adding domain-specific fluid API. [RDShaderSPIRV](../classes/RDShaderSPIRV.md) owns copied bytecode and compiler diagnostics; [RDUniform](../classes/RDUniform.md) describes borrowed resource bindings. [ShaderStage](../classes/RenderingDevice.ShaderStage.md) and [UniformType](../classes/RenderingDevice.UniformType.md) retain their applicable numeric identities.

## Lifetime and execution

A local device owns private RID identities and belongs to its creating thread. Buffer/shader/pipeline/set operations reject other-device or freed identities. Pipelines and sets borrow their shader; sets borrow buffers. Freeing a dependency invalidates borrowers. Caller disposal releases the entire device graph. Resource freeing finishes pending work; device disposal cancels unsubmitted commands and waits for submitted work.

Storage buffers are GPU allocations with copied uploads and explicit reads. Uniform buffers retain host bytes, copied into command data at each dispatch, so subsequent updates cannot rewrite an already recorded dispatch. One compute list is active at a time. Each dispatch ends its native pass, establishing a dependency before the next dispatch; explicit ComputeListAddBarrier preserves that guarantee. ComputeListEnd ends recording, Submit obtains a fence, and Sync waits/releases it. BufferGetData also completes pending writes. Its span overload reuses caller storage; its array overload intentionally creates an independent result.

The current compute profile accepts one static-workgroup `main` SPIR-V entry point, up to eight storage buffers and four uniform buffers. Application descriptor set/binding numbers are remapped internally to native slots. Read-only storage annotations may be relaxed internally while preserving their shader instructions. Payload bounds/instruction structure, descriptor identities and unsupported resource kinds are validated before creation; this is not a full semantic verifier for arbitrary SPIR-V instructions. Push constants, descriptor arrays, device texture/graphics pipelines, specialization constants and asynchronous texture transfers remain separate gaps. StorageBufferUsage.DispatchIndirect adds the executing indirect-command role; buffer device-address creation remains absent until the backend can expose that capability. Unsupported capability and native errors propagate; no algorithm is silently replayed on CPU after a failed GPU submission.

## GPU-directed chains and buffer transfers

`BufferCopy` validates both byte ranges and records storage-to-storage copies on the GPU timeline. It supports all combinations of storage and uniform buffers: a uniform source is snapshotted into the upload; a uniform destination is updated immediately, synchronizing a storage source first. Same-buffer ranges must be disjoint. Byte offsets and copy lengths need no four-byte alignment. `BufferClear` zeros only its range and requires a size divisible by four; its offset is a byte offset. Storage clear reuses the buffer's prepared upload transfer storage. Copy and clear require no active compute list, even for zero bytes. Empty operations still validate ownership, kind and ranges.

Create a command buffer with `StorageBufferCreate(bytes, usage: RenderingDevice.StorageBufferUsage.DispatchIndirect)`. `ComputeListDispatchIndirect(list, commands, offset)` reads three unsigned 32-bit group counts in X/Y/Z order from a four-byte-aligned offset. Prior GPU writes complete before those counts are consumed, including within the same list. Zero in any axis performs no work. The producer is responsible for group counts within device limits (the portable limit is 65535 per axis); the device does not read the counts back to validate them. Buffer identity, indirect role, twelve-byte capacity, alignment, list, pipeline and sets are validated before recording.

[RenderingDeviceTests.Transfers](../../tests/Electron2D.Tests/RenderingDeviceTests.Transfers.cs) is the executable public-API consumer: one shader calculates counts from storage data, a GPU copy moves the command, and another shader dispatches from it. It also executes producer/consumer dispatches in one list. The prepared update/clear/dispatch/copy/span-readback chain measures zero owner-thread managed bytes; this does not measure driver or native allocations.

## Queued readback

`BufferGetDataAsync(buffer, callback, offset, size)` records a request-time snapshot and later supplies an independent byte array to `Action<byte[]>`. Size zero means the remaining buffer, consistently with the synchronous API. The overload accepting `Memory<byte>` and `Action` writes caller-owned storage and reuses prepared queue entries and native download transfer buffers. Keep that memory valid, and do not read or write it until completion. Uniform bytes are copied at request time; GPU bytes are copied at the request's position among recorded commands. Later source mutations cannot replace either snapshot.

The local workflow is: end the compute list, enqueue one or more reads, call Submit, do other CPU work, then call Sync. Neither the request nor Submit invokes callbacks inline. The request does not wait for its own result; starting new recording may wait for the previous submission, as other device recording already does. These automatic waits collect bytes but defer user callbacks. Explicit Sync and nonempty synchronous storage reads deliver completed callbacks on the creating thread; storage reads copy their own result before delivery so callback readback cannot overwrite it. FreeRID completes pending work, removes the resource, then delivers callbacks. Host-only and empty batches also require Submit/Sync; unsubmitted requests remain pending.

Callbacks run once in FIFO order. A callback may issue reads, submit/synchronize, or free resources. Nested delivery is deferred to the outer delivery loop, so a new callback joins the tail after already completed callbacks. All completed callbacks are attempted even if one fails; AggregateException preserves their original exceptions after delivery. Device disposal cancels recorded, submitted and completed-but-undelivered requests, waits for submitted GPU work and releases transfer resources. Disposing inside a callback cancels the rest of that batch. An invalidated caller Memory fails completion and leaves its request available for disposal or retry; no successful callback is invented for a failed copy.

Queue/transfer preparation must cover the largest range and peak concurrent request count. The byte-array overload intentionally allocates an owned result. The Memory overload's prepared two-request small/large cycle measures zero owner-thread managed bytes; driver/native allocator measurements remain absent. [RenderingDeviceTests.Readback](../../tests/Electron2D.Tests/RenderingDeviceTests.Readback.cs) is a complete public-API consumer: two compute dispatches separated by snapshot requests, CPU work between submission and completion, retained results, reusable output storage and lifecycle/error/reentrancy checks.

## Build and example

Application compute shaders can be declared as `Electron2DComputeShader` items and built with [ComputeShaders.targets](../../tools/shaders/ComputeShaders.targets). GLSL/HLSL compile through the existing pinned host toolchain, are validated during the build, and are embedded from `obj/compute` into the consumer assembly. Generated bytecode is not tracked. Shipped executables load compiled resources and need no compiler. The [water playground](water-playground.md) consumes only this public API, PhysicsServer and ordinary rendering/input APIs; its CPU fluid implementation remains application code.

## Verification

`ELECTRON2D_TEST_RENDERING_DEVICE=1 dotnet run --project tests/Electron2D.Tests -c Release` executes the native compute checks. They cover queued request-time snapshots across GLSL/HLSL dispatches, array/memory output, host/empty batches, nested delivery, callback errors and disposal, GPU-produced indirect counts, command copies, zero-group dispatch, all storage/uniform copy directions, partial/unaligned ranges, clear ordering, overlapping-copy rejection, indirect role/offset/lifetime errors, prepared zero managed allocations, arithmetic across ordered dispatches, nontrivial descriptor set/binding numbers, changing uniform data between recorded dispatches, span readback, invalid ranges/sets/thread access, dependency invalidation, shader duplication and resource persistence. The native profile exercised locally is Linux x64/.NET 10 on an NVIDIA GeForce RTX 3090 Ti. Other operating systems, device-loss recovery and native allocator measurements are not established by these checks.

Caller-defined MemoryManager accessors cannot reenter this device while its destination span is being acquired. Attempts to synchronize, mutate or dispose it throw InvalidOperationException before native mapping or state mutation. A failed destination acquisition retains the submitted request for retry or cancellation during disposal. The native readback fixture verifies this guard and invalidated caller memory.

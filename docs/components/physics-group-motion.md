# Physics motion from processing groups

Last updated: 2026-10-25

The current processing group can author its RigidBody linear/angular velocity, axis velocity, sleep request and automatic sleep policy, StaticBody/AnimatableBody surface velocities and CharacterBody desired velocity. Ordinary scene-owner operations keep their existing direct path. Foreign groups and unrelated threads receive no access. Geometry, modes, forces, numerical movement, raw RID operations and direct-state acquisition retain their separate guards.

Before a worker stage, the scene owner prepares each participating physical receiver and captures its observable solver velocity and activity for the current attachment. Workers read that prepared state and their accepted logical inputs. Scalar authoring does not enter a selected implementation on a worker; even registered HasFailure is observed by the owner before borrowing. Static participation remains inactive. Kinematic direct profiles combine solver motion with authored surface velocity; locked profiles suppress native angular motion. CharacterBody velocity is authored state; the main collector still performs MoveAndSlide.

Native motion requests retain per-body order in reusable value storage. After every joined worker stage the original owner publishes them before later main groups or numerical integration. A failed operation retains its cursor and remaining tail; successful prefixes are not repeated. The next owner preparation retries pending input before accepting another worker stage. Readonly implementation hooks can observe the current native prefix without recursively draining later requests. Retirement folds accepted pending motion into scene state, then discards the old queue; a replacement attachment cannot replay it. Private replay restoration also clears obsolete pending requests.

The per-receiver snapshot contains only observable velocity/activity, qualified by attachment generation. It is not a host copy of solver contacts, geometry or constraints. GPU observations reuse selected publication caches when current; explicit stale observations retain their ordinary readback cost. [The cost fixture](../../tests/Electron2D.Tests/PhysicsGroupMotionCosts.cs) compares the same nine-body successful workflow on owner and worker groups and records complete-frame uploads, readbacks, submissions, waits and worker managed bytes. These observations do not establish massive-scene or window FPS acceptance.

[The public consumer](../../tests/PhysicsBackendExtension.Consumer/BackendChecks.GroupMotion.cs) exercises scene and all four direct body modes, a frozen body, both surface roles, character movement, logical reads, real owner queries and selected physical motion. Its registered provider checks readonly input hooks, failed publication/retry, retained ordering and removal/reentry. The measured bracket covers 64 complete physical/query frames after 64 warm frames. Optional calibrated CoreCLR markers are diagnostic controls; an untraced strict result remains necessary. Receipts and rejected candidates are retained in `bin/physics-group-motion/2026-10-25/`.

## Verification on 2026-10-25

The final frozen `prepared` CLR and full-trim `aot-prepared` NativeAOT consumers each pass CPU, NVIDIA GPU and registered-provider profiles with owner and separate physics execution. Every profile retains 64 warm and 64 measured complete frames and strict 0/0 owner/all-thread managed bytes. Twelve additional untraced registered/separate CLR processes also pass. CPU profiles prohibit a graphics ICD; GPU receipts require NVIDIA mappings and reject software devices. NativeAOT receipts reject CoreCLR mappings. Source manifests match before and after each final build (5384 source files, base main `3cd6b903e7fb4f26787f716982dbda305cf8bf2b`).

The final CLR worker-pool suite and both CLR/NativeAOT registered physical-bone owner/separate profiles pass. Existing body-state profiles cover six scene/server owners, four modes, 16 lifecycle cases, 128 changed frames, 576 owner callbacks and 768 queries on all three selected providers. Existing registered motion-transaction owner/separate profiles cover 3514 failure cases and 128 changed frames. These regression receipts retain their own earlier frozen identities. Early eager geometry preparation broke physical-bone failure/retry: motion snapshot preparation now drains pending mode/motion without rebuilding unrelated geometry before its scheduled callback; final physical-bone controls verify that correction.

Earlier strict candidates reported 0/32 bytes, including a calibrated trace that reproduces the failure. `profile-registered-separate-4.1848914` records exactly one 32-byte allocation in measured tag `281612416665129` on an Electron2D worker. Its stack resolves to CoreCLR `StaticsHelpers.GetGCThreadStaticsByIndexSlow`, then `WorkerPoolRuntime.Execute`/`Worker.Run`, with successful stack HRESULT. Pool startup now prepares the construction-context read used by every job before publishing readiness. The final untraced repeated profiles verify this preparation. The consumer also reuses the common blocking collection/finalization helper; that change alone did not remove the 32-byte failure. Earlier failed intervals remain failed; other untraced historical failures have no captured allocation stack. Profiling and isolated successes do not establish the cause of every earlier interval.

Host-activity samples accompany each receipt, so these single observations are not hardware throughput or massive-scene acceptance.

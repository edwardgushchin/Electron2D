# Independent processes and pipes

Last updated: 2026-11-13

## Scope and flow

POSIX argv strings use [tracked UTF8 input storage](../coverage/performance-producers.md#legacy-platform-input-conversion-2026-10-29) and release every prepared argument after native creation or partial failure.

OS process operations use the retained static service. CreateProcess starts a literal executable/argv independently; CreateInstance restarts the current application, including the entry assembly for a framework-dependent host. Execute blocks and appends one captured string after exit, preserving existing collection items. Windows and POSIX stdout/stderr capture merges into one native stream in write order; nonzero exit codes remain ordinary results. Arguments never enter an implicit shell. GetExecutablePath returns the actual native host path, GetCommandLineArgs copies application arguments, and GetCommandLineUserArgs copies the suffix after the first -- or ++ separator.

ExecuteWithPipe returns ProcessPipes with PID, owned bidirectional StandardIO and read-only StandardError FileAccess streams. Pipes are non-seekable. Blocking I/O waits on the caller; nonblocking ReadBytes returns an available prefix immediately without mistaking NotReady for EOF. Exact reads can consume an incomplete prefix before throwing IOException; use byte buffers for incremental framing. A partial write throws PipeWriteException.BytesWritten so retries send only the remainder. Closing/disposal releases streams without killing the independent process. Native SafeHandles also release forgotten streams. IsProcessRunning queries native IDs, GetProcessExitCode retains the most recently owned child status, and Kill terminates only one process, never its descendants. IDs may be reused by the OS. Completed children release native/BCL handles; a small exit-history record remains in the service.

This is cold, blocking/allocating process and I/O work. It is unsuitable for real-time callbacks. The runtime does not impose application-specific deadlines or kill policy. Tooling hosts still own cancellation, deadlines, diagnostics and project orchestration under ADR 0090. Linux/.NET10 with SDL3.4.18 is exercised. Mobile launch adapters and general macOS .app process selection remain exact dependencies. The bounded Windows x64 host profile below now executes; other architectures/sandboxes and the full ADR 0021 matrix remain open. Arbitrary named pipe:// paths remain unavailable; these pipe://PID/channel values identify already-owned streams and do not create a named-pipe connector.

## Windows console and capture

CreateProcess and Execute share the private CreateProcessW launcher in [ProcessPlatform](../classes/ProcessPlatform.md). `openConsole: true` selects CREATE_NEW_CONSOLE even when the parent owns a console; false selects CREATE_NO_WINDOW. CreateInstance and ordinary OpenWithProgram use the default hidden launch. Without capture, a new console obtains its own standard devices; hidden launch retains the parent's standard handles. Execute assigns stdout and merged stderr the same anonymous-pipe write handle, or discards disabled stderr to NUL. Omitted output drains to Stream.Null. There is no delivery-time merge or unread second pipe. Standard input retains the parent's handle.

A native handle allowlist isolates inherited handles. Local pipe writers, thread handles and attribute storage close after launch or failure. Retained SafeProcessHandles preserve all DWORD exit bits, including negative Int32 values, without background-mode substitution. ExecuteWithPipe keeps SDL owners, inherited console identity and per-direction locks. The environment gate serializes both launch mechanisms with environment changes. Win32 launch failures retain Win32Exception; SDL process/pipe failures retain IOException. Closing streams leaves successful independent children alive; failed unpublished setup terminates its own child.

[OSProcesses.Consumer](../../tests/OSProcesses.Consumer/README.md) shares root scenarios through public API only. Test children hide their consoles. GetConsoleWindow and GetConsoleProcessList independently verify a console-owning parent, separate child membership, hidden children, inherited pipe children, CreateInstance and OpenWithProgram. Scenarios include 512 alternating WriteFile calls, concurrent capture, literal Unicode/backslash/quote arguments, UTF8 BOM/malformed-byte decoding, 4 MiB capture/discard, full exit bits and completed code 259, failures, duplex/partial writes, finalization and detached lifetime. Native heaps/performance, other Windows architectures/sandboxes and the complete delivered-platform matrix remain unqualified.

## Post-create ownership and failure verification

The SafeProcessHandle wrapper is allocated before CreateProcessW. From native success through process-handle adoption, local pipe-writer closure and OSProcess construction, a finally guard retains responsibility for both native handles. Only the successful return transfers process ownership. Failure terminates and waits for the unpublished child, closes the raw thread and either the raw or adopted process handle exactly once. Error cleanup explicitly closes the exposed anonymous-pipe client handle: disposing AnonymousPipeServerStream alone does not close that exposed handle. STARTUPINFO size matches the presence of EXTENDED_STARTUPINFO_PRESENT.

The isolated [ProcessAdoption.Tests](../../tests/ProcessAdoption.Tests/README.md) instruments the real launcher at four post-create boundaries without production fault flags or public API. It throws a preallocated OutOfMemoryException and independently observes original raw-handle validity, child retirement through a separately opened native process handle, warmed total native handle counts and a successful independent retry. Sixteen capture/independent and hidden/new-console scenarios execute. The preceding 9c46536c launcher fails immediately with both handles open and a live lost child; the fixture cleans up that deliberate control. Normal runtime and package artifacts are rebuilt without the overlay. The corrected guard passes all sixteen cases in CLR (205 native handles before/after each failure) and strict full-trim NativeAOT (143 before/after); retry succeeds after each failure. Root/public consumer, source CLR/strict NativeAOT and fresh managed-package CLR/strict NativeAOT were rerun after this guard change. These deterministic exception checks do not simulate system-wide exhausted memory or qualify native heap behavior.

## Owned types

[OS](../classes/OS.md) supplies static operations, [ProcessPipes](../classes/ProcessPipes.md) owns the typed dictionary projection, and [PipeWriteException](../classes/PipeWriteException.md) projects consumed-prefix error state. Internal [OSProcess](../classes/OSProcess.md), [ProcessPipeStream](../classes/ProcessPipeStream.md) and [ProcessPipeHandle](../classes/ProcessPipeHandle.md) serialize native lifetime and nonblocking I/O; FileAccess retains one operation lock for seekable files and separate read/write direction locks for process pipes, with existing strict encodings and binary methods. Separate threads may independently drain stdin/stdout and stderr; reads and writes on StandardIO may drain concurrently; each direction remains serialized. Native blocking reads release the process gate between polls so another thread can stop the child.

## Example

This desktop fragment requires a known executable that reads one line, returns stdout/stderr lines and exits. OSProcessTests compiles and exercises the same public path.

```csharp
using var child = OS.ExecuteWithPipe(executable, arguments);
child.StandardIO.WriteLine("request");
child.StandardIO.Flush();
var response = child.StandardIO.ReadLine();
var error = child.StandardError.ReadLine();
var pid = child.PID;
// Dispose streams when finished; OS.Kill(pid) is explicit process policy.
```

## Dependencies and decisions

Uses private Win32 process launch and the approved internal SDL process/IO backend with POSIX status observation, without new packages or vendor edits. ADRs 0004/0020/0095 define typed result/error, stream and service ownership. ADR 0090 separates the runtime primitives from a complete agent/editor workflow. Native SDL pipe streams must retain their process until closure; their native cleanup removes process stream properties before process destruction. [SDL process creation](https://wiki.libsdl.org/SDL3/SDL_CreateProcessWithProperties) and [input](https://wiki.libsdl.org/SDL3/SDL_GetProcessInput) describe native stream readiness/partial writes.

Process-local environment changes through OS.SetEnvironment/UnsetEnvironment are inherited by subsequent launches through both Win32 and SDL native paths. See [environment ownership and directory queries](os-environment.md).

A process launched with ExecuteWithPipe can receive its request through OS.ReadBufferFromSTDIN/ReadStringFromSTDIN and inspect its actual standard handles. The [standard-input component](standard-input.md) verifies this linked public workflow with an independent child.

OS restart-on-exit configuration is a process-wide, desktop-only request with a copied literal argument list. SetRestartOnExit atomically replaces both values; IsRestartOnExitSet reads the flag and GetRestartOnExitArguments returns an independent array, including while disabled. Invalid Unicode, NUL or null elements fail before publication. A single normal managed process-shutdown handler captures the final request and uses CreateInstance. A standalone host must finish its loop cleanup and return; stopping a borrowed loop or returning from Engine.Run alone does not exit its host. The replacement process starts with disabled restart state. Failed native launch reports to standard error and preserves the original exit code; crashes and forced termination do not guarantee shutdown callbacks.

A restart attempt clears its retained flag and arguments before subsequent managed shutdown handlers run. Shutdown capture rejects later setters. A controlled Linux apphost fixture removes only its copied executable and verifies actual launch-failure reporting without changing the original exit status.

CreateInstance relaunches an application executable directly. For a dotnet host it resolves the named entry DLL from AppContext.BaseDirectory and verifies the file before launching, without requiring Assembly.Location. Literal argument and process ownership contracts remain unchanged.

Managed process termination explicitly rejects iOS, tvOS, MacCatalyst and browser profiles before reaching unsupported process APIs. The local iOS-profile platform-analysis build checks this guard; target-native execution remains a separate gate.

## Specified application launch

OS.OpenWithProgram(programPath, paths) opens ordered host file/directory paths in a chosen application. Ordinary executable launches share CreateProcess validation, independent lifetime and completed-child reaping; no shell interprets spaces, quotes, semicolons, dollar expressions or leading dashes. An empty path list launches the application without arguments, and individual empty strings remain literal arguments. The complete input is checked before launch. Virtual executable paths resolve through ProjectSettings; file arguments retain their exact supplied value, so explicitly globalize virtual resource paths first.

On macOS a .app suffix selects /usr/bin/open with separate -a, absolute bundle path, -- and path arguments. The call waits for the request launcher, not the application, and a nonzero launcher exit becomes IOException. This supplies specified-bundle selection independently of CreateProcess's remaining general bundle launch gap. On ordinary desktop executable launches the call returns after process creation. The typed void/exception result projects the reference Error result; success proves request acceptance, not that the chosen application opened every file. Unsupported mobile/browser process hosts reject before launch.

ELECTRON2D_TEST_OPEN_WITH_PROGRAM=1 exercises OSOpenWithProgramTests with the Release runner. Its fresh application waits on an explicit file gate after launch has returned, then reports the exact argv and exits through the ordinary OS process owner. Empty lists, empty strings, Unicode, quotes, shell-looking text, leading separators, caller array mutation, null/NUL/invalid-UTF16 input and missing-program cleanup are covered on Linux and Windows x64. The operation is cold and allocating. macOS bundle selection, other Windows architectures, foreign sandboxes and user application acceptance require their native hosts.

# Shader materials

Last updated: 2026-09-23

## Scope and implementation state

The rendering integration contains executable canvas fragment shaders, material uniform buffers and sampled image textures. This is partial shader support under [ADR 0028](../decisions/rendering.md#adr-0028): matrix shapes beyond float2x2, nested structs and custom vertex programs remain unfinished. The native verification covers Linux Wayland/Vulkan; other GPU backends and platforms are unverified.

Public resources are [Shader](../classes/Shader.md), [Shader.Mode](../classes/Shader.Mode.md), [Material](../classes/Material.md), [ShaderMaterial](../classes/ShaderMaterial.md), [CanvasItemMaterial](../classes/CanvasItemMaterial.md), [Texture](../classes/Texture.md), [ImageTexture](../classes/ImageTexture.md) and [AtlasTexture](../classes/AtlasTexture.md). CanvasItemMaterial's fixed blending is documented in [canvas rendering](canvas-rendering.md#fixed-canvas-blending). Their managed state belongs to the Resources domain. The rendering backend owns GPU devices and pipelines; resources contain no native handles.

## Import and runtime flow

The verified source profiles are HLSL 2021 with Shader Model 6.0 (`ps_6_0`, internal `vs_6_0`) and GLSL `#version 450` targeting Vulkan 1.0, all with entry point `main`. The [import tool profile](../../tools/shaders/README.md#verified-source-and-bytecode-profiles) records options and executable macro checks. The pinned Shadercross package's [native source](https://github.com/edwardgushchin/SDL_shadercross/blob/e55cf5e31ced6f3d1be5cc6d0c50e99384f9f4ba/src/SDL_shadercross.c) supplies the HLSL stage profiles and binding-preservation flags; its effective HLSL language default is verified by the importer test. These are compiler targets for the supported canvas interface, not full language-feature acceptance.

Imported fixtures use SPIR-V 1.0 and baseline `Shader` capability. Import validates the Vulkan 1.0 environment. Runtime header checks admit SPIR-V 1.0–1.6, then apply resource/interface and backend checks without full instruction validation. A structurally accepted header does not establish additional SPIR-V feature or target support.

1. `tools/shaders/ShaderImport.csproj` compiles HLSL through the pinned SDL3-CS ShaderCross/DXC integration, or GLSL through the bundled `glslangValidator` reporting `Glslang Version: 11:16.4.0`. It also accepts external SPIR-V. The [import tool](../../tools/shaders/README.md) carries the exact glslang and `spirv-val` executables; it never searches `PATH` for them.
2. Every input passes `spirv-val` (`SPIRV-Tools v2026.3`, target `vulkan1.0`) and the same engine interface/reflection checks. Only a successful import atomically replaces changed destination `.spv` bytes; identical output preserves its timestamp. Diagnostics include the source path and stage; compiler diagnostics retain source locations.
3. `Shader.CreateFromSPIRV` and `SetSPIRV` copy the bytes and perform the same structural, capability, resource-layout and interface checks for every input origin. These checks do not duplicate the import tool's instruction-level validator. Runtime source compilation is absent.
4. An immutable `ShaderProgram` publishes code, buffer sizes, member layouts and typed descriptors together. SPIRV-Cross reflects active resources and members; SDL_shadercross reflects stage interfaces and translates programs for the active GPU backend. The SPIRV-Cross C library is already shipped in `SDL3-CS.Linux.Shadercross`; member reflection introduces no additional package.
5. `ShaderMaterial` owns mutable uniform buffers. Before a draw, the renderer obtains the current program/state and pushes each buffer through SDL3-CS `PushGPUFragmentUniformData`. Resource mutation and upload serialize through the material gate. No callback runs under that gate.
6. Reloading a shader rebuilds material buffers on their next access. Matching names, shader element types (including integer signedness and logical boolean width) and array lengths retain values even if bindings and offsets change. New or incompatible members start at their typed defaults: identity for float2x2 matrices and zero for other stored components. GPU pipelines are cached by program payload and blend mode and discarded when unused.

## Current shader interface

- One fragment entry point named `main`; optional inputs are float4 color at location zero and float2 UV at location one, and output is float4 at location zero. Framebuffer position is available as the stage builtin.
- SPIR-V input is little-endian, word-aligned, bounded to 16 MiB and the baseline `Shader` capability. The import command additionally runs `spirv-val`. Runtime resource loading checks the documented payload and interface contract for all origins; it is not a full SPIR-V specification verifier. Native translation/program-creation errors propagate before a successful draw is reported.
- At most four uniform buffers, descriptor set 3, unique contiguous bindings starting at zero. Each buffer is at most 16 KiB. Std140 alignment and array strides are checked, and uploads include final 16-byte block padding.
- Uniform member names are nonblank, ordinal/case-sensitive and unique across buffers. Compilers must retain names. Reflection rejects overlapping members and members outside their buffer.
- Types currently mapped to C#: `bool`, `float`, `int`, `uint`, `Vector2`, `Vector3` for float3, `Transform` for float2x2, `Vector4`, `Vector2i`, `Vector3i`, `Vector4i`. `Color` aliases float3 and float4; `Rect` aliases float4; integer vectors carry either signed or unsigned shader components. Boolean vectors use int component masks; see [boolean type information](#boolean-type-information). See [vector value mappings](#vector-value-mappings). A fixed one-dimensional array uses the same element mapping and 1–1024 elements within the buffer size limit.
- Floating-point material values must be finite. Setters validate the complete input before writing. Matrices initially contain identity; other stored uniform components contain zero (float3 Color reads reconstruct alpha one); source-level default values are not extracted.
- Storage resources, push constants, nested structures and matrices other than float2x2 fail explicitly until their executable integration is present. Other numeric mappings remain unimplemented. These restrictions are implementation gaps, not a claim that either language is fully supported.

## Vector value mappings

| Shader element | Typed values | Stored/read components |
| --- | --- | --- |
| GLSL vec3 / HLSL float3 | Vector3, Color | XYZ, or RGB without gamma conversion; Color reads reconstruct alpha one. |
| GLSL vec4 / HLSL float4 | Vector4, Color, Rect | XYZW, RGBA, or position.x/position.y/size.x/size.y. |
| GLSL uvec2 / HLSL uint2 | Vector2i | Component bit patterns, including negative C# int values. |
| GLSL ivec3/uvec3 / HLSL int3/uint3 | Vector3i | Component bit patterns, including negative C# int values. |
| GLSL uvec4 / HLSL uint4 | Vector4i | Component bit patterns, including negative C# int values. |

Each mapping supports individual values and fixed one-dimensional arrays through the same parameter API. A float3 occupies twelve bytes at a sixteen-byte-aligned offset; the next float can occupy the fourth component slot. Array elements use the reflected std140 stride. Writes, copies and reload migration never copy Color alpha into a neighboring member. All supplied float components must be finite, including unused Color alpha. Rect sizes need not be positive because these are shader numeric values, not rectangle geometry operations.

Canonical descriptors are Vector3 for float3, Vector4 for float4 and Vector2i/Vector3i/Vector4i for signed or unsigned integer vectors. Getter/revert values use zero stored components and alpha one for float3 Color. Integer values retain bits: an int component of -1 reaches a uvec as 4294967295. Changing signedness during reload resets that parameter even though its C# carrier type is unchanged. Matching arrays migrate by name, type and length; layout changes can move them between buffers.

The [official shader value table](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/shading_language.html#setting-uniforms-from-code) and the pinned [material packing source](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/storage_rd/material_storage.cpp) establish the RGB/rectangle mappings and signed integer carriers for unsigned vectors. Electron2D's typed storage returns the represented components rather than retaining an arbitrary input Variant. [ADR 0033](../decisions/core-math.md#adr-0033) defines the numeric three-component vectors. Matrix shapes beyond float2x2, source defaults and color-conversion hints remain unfinished.

## Matrix parameters

GLSL `mat2` and HLSL `float2x2` map to the X/Y basis columns of `Transform`, including fixed arrays. Origin is not represented; readers reconstruct it as zero. Setters require all six supplied floats to be finite, including Origin. Initial and descriptor-revert values are identity for each matrix element; an explicitly assigned `default(Transform)` remains a zero matrix. The pinned [material packing/defaults implementation](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/storage_rd/material_storage.cpp) supplies the mat2 basis mapping and identity default. No new public matrix type is added.

The engine's canonical value follows SPIR-V logical columns. Reflection requires an explicit, unique RowMajor/ColMajor order, a MatrixStride of at least 16 bytes and divisible by 16, aligned offsets and sufficient non-overlapping buffer space. Array strides and lengths have the existing fixed-array checks. Every write/read honors the reflected order and stride. Migration converts through the logical basis, preserving values when row/column order, matrix stride, array stride, offsets or buffer bindings change. Padding and neighboring scalar values are preserved.

DXC represents HLSL matrices by their transposes in SPIR-V and reverses storage-order decorations; see its [matrix representation documentation](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/SPIR-V.rst#vectors-and-matrices). Therefore equivalent basis application is `basis * point` in GLSL and `mul(point, basis)` in HLSL (or `mul(transpose(basis), point)`). In both sources `basis[0]` accesses the supplied X vector and `basis[1]` accesses Y, although GLSL calls these columns and HLSL calls them rows. Selecting row/column storage does not change that value contract. External SPIR-V follows the same logical-column rule regardless of its producer.

Partial source snippets (inside supported fragment buffers/programs):

```glsl
layout(set = 3, binding = 0, std140) uniform Material { mat2 basis; };
// In main: vec2 transformed = basis * point;
```

```hlsl
cbuffer Material : register(b0, space3) { float2x2 basis; };
// In main: float2 transformed = mul(point, basis);
```

## Render time

A fragment shader may declare one case-sensitive uniform member `float TIME` in any supported descriptor-set-3 buffer. HLSL and GLSL use the same rule; externally compiled SPIR-V must preserve the member name and meet the same interface checks. Binding/offset, padding, contiguous slots and std140 layout are reflected normally. TIME requires a non-array float32 scalar; textures, vectors, integers, arrays, duplicate member names and vertex TIME are rejected. Public custom vertex shaders remain outside the current stage interface. Lowercase `time` is an ordinary material parameter.

TIME is engine input, omitted from Shader.GetShaderUniformList and material property discovery. Material getters/setters and shader default-texture methods reject it. Material duplication and reload migrate user values only; each current program carries its own TIME layout, including when the member moves between buffers. A TIME-only buffer remains allocated/uploaded even though there are no material descriptors. Before each draw, MaterialState writes the current value under the same gate as parameter updates, then pushes the complete padded buffers. No resource Changed event, QueueRedraw or steady-state allocation is required. Nodes and distinct/shared materials in a frame receive the same clock.

RenderingServer's per-run clock advances after FramePreDraw using the process delta captured before callbacks. It honors TimeScale, continues while the tree is paused, and wraps by the active RenderingTimeRolloverSeconds setting (default 3600). Base/feature overrides apply on the next submitted frame. Disabled rendering/hidden root skips advancement. The engine uses double precision and converts to float32 at upload; large values lose precision, and a TIME-using shader rejects a clock outside finite float32 range before drawing. A fresh renderer starts at zero. Compatibility rejects shader materials explicitly.

Minimal fragment buffer declarations (partial snippets; the program must actually read TIME):

```hlsl
cbuffer Frame : register(b0, space3) { float TIME; };
```

```glsl
layout(set = 3, binding = 0, std140) uniform Frame { float TIME; };
```

The [official canvas built-in reference](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/canvas_item_shader.html#global-built-ins) defines scaled, pause-independent, wrapping seconds. The pinned [canvas renderer](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp) maps TIME to frame data; [clock accumulation](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_compositor_rd.cpp) and the [prior clock audit](canvas-rendering.md#animation-intervals-and-rectangles) establish ordering. Explicit uniform declarations are the HLSL/GLSL projection; no new public C# declaration is introduced.

## Texture bindings and pixel ownership

- At most sixteen fragment texture bindings in descriptor set 2, with unique contiguous slots starting at zero. Names are nonblank, case-sensitive and unique across textures and uniform members.
- GLSL uses combined `sampler2D` resources. HLSL uses paired `Texture2D<float4>` and `SamplerState` declarations at the same binding; reflection checks actual image/sampler pairings in sampling operations. These are shader-language intrinsic names, not engine resource names.
- Only ordinary float-sampled 2D images are integrated. Texture arrays, depth comparison, multisampling, storage images and vertex textures fail explicitly. Resource reflection uses active variables, matching SDL_shadercross; unused declarations do not add material slots.
- `Texture` derives from Resource and ImageTexture, AtlasTexture, CurveTexture and CurveXYZTexture derive directly from Texture. All textures are 2D by product definition; there is no separate dimension-neutral parent or dimension suffix in the public type name.
- `AtlasTexture` borrows a source and maps regions/margins through virtual drawing, including nested views. Its CPU image excludes margins; named material bindings resolve to full source storage and share the GPU allocation. Only nested atlas changes forward; Sprite redraws on view changes. Stored view state participates in resource duplication and packed-scene local ownership. See [AtlasTexture](../classes/AtlasTexture.md) for zero-axis, opacity, clipping and no-tiling semantics.
- `ImageTexture.CreateFromImage` and SetImage copy pixels. SetImage resets logical size and replaces allocation identity; Update requires matching original dimensions/format/mips and retains logical overrides and allocation identity. GetImage returns an independent original image. Size overrides use zero to retain an axis, reject negative axes, and never resample pixels.
- [Curve textures](curves.md) synchronously bake borrowed scalar curves to RF/RGBF storage. Texture.GetWidth/GetHeight/GetSize are queries; generated textures expose a writable Width. Source changes preserve compatible allocation identity. Both original formats currently upload as RGBA32Float, so red-only mode reduces CPU storage but does not reduce GPU allocation.
- [Gradient textures](gradients.md) lazily generate RGBA8/RGBAF ramp or planar fills. Source notifications invalidate without forwarding texture Changed; capture before draw refreshes pixels while retaining geometry. Null source freezes prior pixels. Native GPU HDR and both shader languages are verified; tested compatibility drivers reject unavailable HDR precision explicitly.
- GPU upload accepts uncompressed byte and normalized/float formats. Byte formats convert to RGBA8; other accepted formats convert to RGBA32Float, preserving HDR values. Original image data and metadata remain unchanged. Compressed and integer-sampled formats remain explicit gaps. The backend checks sampling-format support before allocation.
- All mip levels upload before drawing. Updates reuse allocation with native cycling; upload completion is recorded only after successful submission. Per-renderer texture and binding caches are pruned when no longer used, and GPU resources are released during shutdown. Logical resources remain caller-owned.
- Custom Texture subclasses provide GetWidth(), GetHeight() and a caller-owned GetImage copy. The renderer caches copied pixels until Changed. ImageTexture snapshots are immutable. Missing, uninitialized or disposed bindings fail before drawing.
- Materials set borrowed overrides through `SetShaderParameter(string, Texture?)`; null resolves the borrowed Shader default. The nongeneric getter returns the explicit override. Shader defaults use Set/GetDefaultTextureParameter with index zero. Both paths participate in typed descriptors, graph-preserving resource duplication and name-based migration across shader reload.
- Material texture sampling uses linear filtering, clamp-to-edge coordinates and base-level LOD, independently of canvas sampling policies. Configurable sampler state remains pending; ordinary texture drawing is described below.

The [SDL uniform upload contract](https://wiki.libsdl.org/SDL3/SDL_PushGPUFragmentUniformData) requires std140-compatible data. The engine obtains actual member offsets from SPIRV-Cross and validates alignment before accepting the program.

## Named sampler defaults

Named material textures use linear minification/magnification, clamp-to-edge addressing and LOD restricted to zero. This includes explicit `textureLod`/`SampleLevel`: positive and negative requested levels clamp to the base level. Texture storage still uploads every mip; [canvas mip sampling](canvas-rendering.md#texture-sampling) verifies their use through ordinary drawing and reserved TEXTURE. Configurable named sampler filtering, repeat, mipmaps and anisotropy remain unfinished. HLSL SamplerState declarations and GLSL sampler2D resources do not encode those settings in the accepted SPIR-V interface.

The pinned [canvas compiler actions](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp) select FILTER_LINEAR and REPEAT_DISABLE for ordinary material textures, while TEXTURE uses a custom canvas sampler. The pinned [sampler allocation](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/storage_rd/material_storage.cpp) sets linear min/mag and max_lod zero for that filter. Electron2D uses the existing GPU sampler cache for the same default. CanvasItem/Viewport filter/repeat/anisotropy properties affect reserved TEXTURE, independently of named material samplers.

## Boolean type information

Both source importers preserve logical booleans even though the GPU buffer representation uses unsigned 32-bit components. HLSL source types come from a second DXC compilation to DXIL through the existing SDL3-CS ShaderCross binding, then IDxcUtils/ID3D12ShaderReflection from its already packaged DXC library. DXC's SPIR-V debug types also describe lowered uint, so they cannot distinguish these fields. The reflection compilation defines the Vulkan 1.0 target macros used by the SPIR-V pass; resource names map it to the actual SPIR-V bindings, including `vk::binding` and `ConstantBuffer<T>`. DXIL is a temporary import reflection input, not a shipped game artifact. GLSL source types come from a second glslang `-gV` pass using `NonSemantic.Shader.DebugInfo.100`. Both passes retain include/preprocessor behavior and compiler diagnostics. The importer checks the typed physical layout before writing metadata, then runs final `spirv-val` and ordinary runtime interface validation on the resulting artifact. No new native package is introduced.

Logical types are stored in standard SPIR-V 1.0 `OpString` instructions, one per reflected boolean member, with this UTF-8 payload:

```text
Electron2D:bool:1:<width>:<array-length>:<base64-utf8-member-name>
```

Width is 1 through 4; length is zero for an individual value or 1 through 1024 for a fixed array. Names must be nonblank and unique, and must identify a member of an active buffer. Metadata must match unsigned 32-bit scalar/vector storage and its exact width/array length; all ordinary buffer alignment, size, stride, binding and overlap checks still apply. Malformed UTF-8/base64, duplicate/absent names, unknown schema versions and mismatched shapes fail before a Shader version or imported output is replaced. The importer emits records sorted by ordinal name. External producers can emit the identical schema and enter the same checks. Metadata declares the producer's logical interpretation; it does not prove the original source type. Unannotated modules keep the physical numeric mapping (including the existing rejection of unmapped uint3). Stripping these strings also strips logical type information. `GetSPIRV`, reload and resource copying retain it without sidecars.

| Source element | C# element | Stored and returned value |
| --- | --- | --- |
| bool | bool | One uint32 component, normalized to zero or one. |
| bool2 / bvec2 | int | Low two bits select X/Y. |
| bool3 / bvec3 | int | Low three bits select X/Y/Z. |
| bool4 / bvec4 | int | Low four bits select X/Y/Z/W. |

Higher mask bits are ignored; readers return only the represented low bits. Fixed arrays use `bool[]` or `int[]` descriptors and span setters, one C# element per logical shader element, with reflected padding handled internally. Defaults/reverts are false or zero masks. Reload preserves matching names, logical widths and array lengths across buffer changes; conversion between numeric and boolean storage or between boolean widths resets the value. An array length of one remains distinct from an individual value.

The pinned [material packing source](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/storage_rd/material_storage.cpp) establishes bool normalization and integer masks for individual bvec values. Under [ADR 0005](../decisions/core-object-runtime.md#adr-0005), Electron2D uses the same scalar mapping per array element: bool arrays use C# bool values; bvec arrays use one int mask per vector instead of an untyped collection or a packed stream of integer components. This preserves shader component values while keeping the array API uniform and avoiding a new spatial vector family.

For an imported fixture declaring these names (partial consumer snippet):

```csharp
material.SetShaderParameter("enabled", true);
material.SetShaderParameter("triple", 0b101);
material.SetShaderParameter<bool>("switches", stackalloc bool[] { true, false, true });
material.SetShaderParameter<int>("pairs", stackalloc int[] { 0b01, 0b10 });
bool enabled = material.GetShaderParameter<bool>("enabled");
int triple = material.GetShaderParameter<int>("triple");
```

## Ordinary texture drawing

Texture.Draw, DrawRect and DrawRectRegion, and the corresponding CanvasItem methods, record borrowed resources during OnDraw. Hardware backends support nearest/linear canvas sampling; software supports nearest. Both paths support source-alpha modulation, stretching, repeat, logical-size overrides, source regions, reflection and transpose. Source clipping preserves interior UV interpolation and clamps the half-texel borders. Geometry uses per-command texture batches in scene order. Texture updates and replacement are visible without QueueRedraw; a disposed or unreadable drawn texture aborts the frame.

The built-in fragment shader multiplies the command sample by drawing color. User shaders may declare `TEXTURE` at descriptor set 2, binding 0; the renderer supplies the command texture or an opaque white pixel for untextured geometry. This reserved binding is excluded from material descriptors and setters. Additional named texture parameters follow the same contiguous binding rules. User fragment programs decide how to combine the sample and color; incoming color is the drawing/modulation product.

Compatibility uploads the base mip level and checks native high-precision formats and non-power-of-two wrapping support before drawing. Unsupported operations fail explicitly. The pinned software driver has an incorrect rectangle shortcut for transposed/constant UVs; textured triangles are submitted separately on that driver. GPU sampling retains all stored mip levels. CanvasItem and Viewport sampling policies, mipmaps and anisotropy are integrated for the reserved TEXTURE sampler; see the [sampling matrix](canvas-rendering.md#texture-sampling). Named material sampler configuration remains pending.

CanvasTextureTests checks three retained frames (initial pixels, Update, then SetImage with new size/format), overrides, null/invalid/disposed resources, uninitialized textures, source regions, transpose, repeat, color/alpha and both imported shader languages. GPU readback verifies clipped and unclipped UV values and unchanged interior interpolation with logical size overrides. A warmed geometry test measures zero managed allocation across 1,000 replays. Linux Wayland GPU/compatibility and dummy/software runs passed; HDR is retained on GPU and explicitly rejected by the tested compatibility drivers lacking native float-texture support.

## Ownership, copying and tooling

Nodes borrow materials; materials borrow shaders and textures; shaders borrow default textures. Disposing either consumer does not dispose its shared resource. The material's copy hook independently copies values and applies the requested resource graph policy to its shader and texture bindings, preserving shared aliases. Clearing `Shader` discards parameter state. `GetShaderUniformList()` returns typed `PropertyDescriptor<ShaderMaterial, T>` values; material property discovery prefixes their names with `shader_parameter/` to avoid collisions with resource properties.

Shader and material state access is serialized. Arrays returned to callers are copies. Scalar/vector and span setters reuse initialized buffers; the current executable check measures zero managed bytes across 2,000 repeated update/read/capture iterations after warmup. A separate native frame check covers capture through submission with eight mixed texture/geometry nodes, HLSL/GLSL materials and twenty measured frames after twenty warmup frames: zero managed bytes on Wayland GPU/Vulkan, compatibility and dummy/software. This does not measure the host event loop, resource loading, readback, arbitrary callbacks or frame time.

ShaderImport is a separate engine build executable. Its friend-assembly access reuses the internal SPIR-V interface validator and SDL3-CS HLSL compiler binding. The runtime does not reference or launch the tool. Games, examples and the future editor consume public runtime resources and imported artifacts; this build-tool access grants them no access to engine internals.

`tools/shaders/build_toolchain.py` builds glslang 16.4.0, SPIRV-Tools v2026.3 and their matching SPIRV-Headers from the revisions and archive SHA-256 hashes in `toolchain.lock.json`. Source and build caches stay under ignored `obj/`. Compiler libraries are statically linked into the two CLI tools, with standard Linux C/C++ runtime libraries remaining system dependencies. Publishing ShaderImport copies the executables, lock and upstream licenses into its own `toolchain/` directory. None of those build-tool files is included by `Electron2D.csproj`. Linux x64 is the currently packaged host; other tool hosts and binary reproducibility across C++ toolchains remain unverified.

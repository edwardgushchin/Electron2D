# Shader materials

Last updated: 2026-09-22

## Scope and implementation state

The rendering integration contains executable canvas fragment shaders, material uniform buffers and sampled image textures. This is partial shader support under [ADR 0028](../decisions/rendering.md#adr-0028): matrices, nested structs and custom vertex programs remain unfinished. The native verification covers Linux Wayland/Vulkan; other GPU backends and platforms are unverified.

Public resources are [Shader](../classes/Shader.md), [Shader.Mode](../classes/Shader.Mode.md), [Material](../classes/Material.md), [ShaderMaterial](../classes/ShaderMaterial.md), [Texture](../classes/Texture.md) and [ImageTexture](../classes/ImageTexture.md). Their managed state belongs to the Resources domain. The rendering backend owns GPU devices and pipelines; resources contain no native handles.

## Import and runtime flow

The verified source profiles are HLSL 2021 with Shader Model 6.0 (`ps_6_0`, internal `vs_6_0`) and GLSL `#version 450` targeting Vulkan 1.0, all with entry point `main`. The [import tool profile](../../tools/shaders/README.md#verified-source-and-bytecode-profiles) records options and executable macro checks. The pinned Shadercross package's [native source](https://github.com/edwardgushchin/SDL_shadercross/blob/e55cf5e31ced6f3d1be5cc6d0c50e99384f9f4ba/src/SDL_shadercross.c) supplies the HLSL stage profiles and binding-preservation flags; its effective HLSL language default is verified by the importer test. These are compiler targets for the supported canvas interface, not full language-feature acceptance.

Imported fixtures use SPIR-V 1.0 and baseline `Shader` capability. Import validates the Vulkan 1.0 environment. Runtime header checks admit SPIR-V 1.0–1.6, then apply resource/interface and backend checks without full instruction validation. A structurally accepted header does not establish additional SPIR-V feature or target support.

1. `tools/shaders/ShaderImport.csproj` compiles HLSL through the pinned SDL3-CS ShaderCross/DXC integration, or GLSL through the bundled `glslangValidator` reporting `Glslang Version: 11:16.4.0`. It also accepts external SPIR-V. The [import tool](../../tools/shaders/README.md) carries the exact glslang and `spirv-val` executables; it never searches `PATH` for them.
2. Every input passes `spirv-val` (`SPIRV-Tools v2026.3`, target `vulkan1.0`) and the same engine interface/reflection checks. Only a successful import atomically replaces changed destination `.spv` bytes; identical output preserves its timestamp. Diagnostics include the source path and stage; compiler diagnostics retain source locations.
3. `Shader.CreateFromSPIRV` and `SetSPIRV` copy the bytes and perform the same structural, capability, resource-layout and interface checks for every input origin. These checks do not duplicate the import tool's instruction-level validator. Runtime source compilation is absent.
4. An immutable `ShaderProgram` publishes code, buffer sizes, member layouts and typed descriptors together. SPIRV-Cross reflects active resources and members; SDL_shadercross reflects stage interfaces and translates programs for the active GPU backend. The SPIRV-Cross C library is already shipped in `SDL3-CS.Linux.Shadercross`; member reflection introduces no additional package.
5. `ShaderMaterial` owns mutable uniform buffers. Before a draw, the renderer obtains the current program/state and pushes each buffer through SDL3-CS `PushGPUFragmentUniformData`. Resource mutation and upload serialize through the material gate. No callback runs under that gate.
6. Reloading a shader rebuilds material buffers on their next access. Matching names, element types and array lengths retain values even if bindings and offsets change. New or incompatible members start at zero. GPU pipelines are cached by program payload and discarded when unused.

## Current shader interface

- One fragment entry point named `main`; optional inputs are float4 color at location zero and float2 UV at location one, and output is float4 at location zero. Framebuffer position is available as the stage builtin.
- SPIR-V input is little-endian, word-aligned, bounded to 16 MiB and the baseline `Shader` capability. The import command additionally runs `spirv-val`. Runtime resource loading checks the documented payload and interface contract for all origins; it is not a full SPIR-V specification verifier. Native translation/program-creation errors propagate before a successful draw is reported.
- At most four uniform buffers, descriptor set 3, unique contiguous bindings starting at zero. Each buffer is at most 16 KiB. Std140 alignment and array strides are checked, and uploads include final 16-byte block padding.
- Uniform member names are nonblank, ordinal/case-sensitive and unique across buffers. Compilers must retain names. Reflection rejects overlapping members and members outside their buffer.
- Types currently mapped to C#: `float`, `int`, `uint`, `Vector2`, `Vector4`, `Vector2I`, `Vector4I`. `Color` aliases a float4 without color-space conversion. A fixed one-dimensional array uses the same element mapping and 1–1024 elements within the buffer size limit.
- Floating-point material values must be finite. Setters validate the complete input before writing. Uniforms initially contain zero; source-level default values are not extracted.
- Storage resources, push constants, nested structures and matrices fail explicitly until their executable integration is present. Boolean and other numeric mappings remain unimplemented. These restrictions are implementation gaps, not a claim that either language is fully supported.

## Texture bindings and pixel ownership

- At most sixteen fragment texture bindings in descriptor set 2, with unique contiguous slots starting at zero. Names are nonblank, case-sensitive and unique across textures and uniform members.
- GLSL uses combined `sampler2D` resources. HLSL uses paired `Texture2D<float4>` and `SamplerState` declarations at the same binding; reflection checks actual image/sampler pairings in sampling operations. These are shader-language intrinsic names, not engine resource names.
- Only ordinary float-sampled 2D images are integrated. Texture arrays, depth comparison, multisampling, storage images and vertex textures fail explicitly. Resource reflection uses active variables, matching SDL_shadercross; unused declarations do not add material slots.
- `Texture` derives from Resource and ImageTexture derives directly from Texture. All textures are 2D by product definition; there is no separate dimension-neutral parent or dimension suffix in the public type name.
- `ImageTexture.CreateFromImage` and SetImage copy pixels. SetImage resets logical size and replaces allocation identity; Update requires matching original dimensions/format/mips and retains logical overrides and allocation identity. GetImage returns an independent original image. Size overrides use zero to retain an axis, reject negative axes, and never resample pixels.
- GPU upload accepts uncompressed byte and normalized/float formats. Byte formats convert to RGBA8; other accepted formats convert to RGBA32Float, preserving HDR values. Original image data and metadata remain unchanged. Compressed and integer-sampled formats remain explicit gaps. The backend checks sampling-format support before allocation.
- All mip levels upload before drawing. Updates reuse allocation with native cycling; upload completion is recorded only after successful submission. Per-renderer texture and binding caches are pruned when no longer used, and GPU resources are released during shutdown. Logical resources remain caller-owned.
- Custom Texture subclasses provide Width, Height and a caller-owned GetImage copy. The renderer caches copied pixels until Changed. ImageTexture snapshots are immutable. Missing, uninitialized or disposed bindings fail before drawing.
- Materials set borrowed overrides through `SetShaderParameter(string, Texture?)`; null resolves the borrowed Shader default. The nongeneric getter returns the explicit override. Shader defaults use Set/GetDefaultTextureParameter with index zero. Both paths participate in typed descriptors, graph-preserving resource duplication and name-based migration across shader reload.
- Material texture sampling currently uses nearest filtering and clamp-to-edge coordinates. Configurable sampler state remains pending; ordinary texture drawing is described below.

The [SDL uniform upload contract](https://wiki.libsdl.org/SDL3/SDL_PushGPUFragmentUniformData) requires std140-compatible data. The engine obtains actual member offsets from SPIRV-Cross and validates alignment before accepting the program.

## Ordinary texture drawing

Texture.Draw, DrawRect and DrawRectRegion, and the corresponding Node methods, record borrowed resources during OnDraw. Both backends support nearest sampling, source-alpha modulation, stretching, repeat, logical-size overrides, source regions, reflection and transpose. Source clipping preserves interior UV interpolation and clamps the half-texel borders. Geometry uses per-command texture batches in scene order. Texture updates and replacement are visible without QueueRedraw; a disposed or unreadable drawn texture aborts the frame.

The built-in fragment shader multiplies the command sample by drawing color. User shaders may declare `TEXTURE` at descriptor set 2, binding 0; the renderer supplies the command texture or an opaque white pixel for untextured geometry. This reserved binding is excluded from material descriptors and setters. Additional named texture parameters follow the same contiguous binding rules. User fragment programs decide how to combine the sample and color; incoming color is the drawing/modulation product.

Compatibility uploads the base mip level and checks native high-precision formats and non-power-of-two wrapping support before drawing. Unsupported operations fail explicitly. The pinned software driver has an incorrect rectangle shortcut for transposed/constant UVs; textured triangles are submitted separately on that driver. GPU sampling retains all stored mip levels. Filtering/sampler configuration remains pending.

CanvasTextureTests checks three retained frames (initial pixels, Update, then SetImage with new size/format), overrides, null/invalid/disposed resources, uninitialized textures, source regions, transpose, repeat, color/alpha and both imported shader languages. GPU readback verifies clipped and unclipped UV values and unchanged interior interpolation with logical size overrides. A warmed geometry test measures zero managed allocation across 1,000 replays. Linux Wayland GPU/compatibility and dummy/software runs passed; HDR is retained on GPU and explicitly rejected by the tested compatibility drivers lacking native float-texture support.

## Ownership, copying and tooling

Nodes borrow materials; materials borrow shaders and textures; shaders borrow default textures. Disposing either consumer does not dispose its shared resource. The material's copy hook independently copies values and applies the requested resource graph policy to its shader and texture bindings, preserving shared aliases. Clearing `Shader` discards parameter state. `GetShaderUniformList()` returns typed `PropertyDescriptor<ShaderMaterial, T>` values; material property discovery prefixes their names with `shader_parameter/` to avoid collisions with resource properties.

Shader and material state access is serialized. Arrays returned to callers are copies. Scalar/vector and span setters reuse initialized buffers; the current executable check measures zero managed bytes across 2,000 repeated update/read/capture iterations after warmup. A separate native frame check covers capture through submission with eight mixed texture/geometry nodes, HLSL/GLSL materials and twenty measured frames after twenty warmup frames: zero managed bytes on Wayland GPU/Vulkan, compatibility and dummy/software. This does not measure the host event loop, resource loading, readback, arbitrary callbacks or frame time.

ShaderImport is a separate engine build executable. Its friend-assembly access reuses the internal SPIR-V interface validator and SDL3-CS HLSL compiler binding. The runtime does not reference or launch the tool. Games, examples and the future editor consume public runtime resources and imported artifacts; this build-tool access grants them no access to engine internals.

`tools/shaders/build_toolchain.py` builds glslang 16.4.0, SPIRV-Tools v2026.3 and their matching SPIRV-Headers from the revisions and archive SHA-256 hashes in `toolchain.lock.json`. Source and build caches stay under ignored `obj/`. Compiler libraries are statically linked into the two CLI tools, with standard Linux C/C++ runtime libraries remaining system dependencies. Publishing ShaderImport copies the executables, lock and upstream licenses into its own `toolchain/` directory. None of those build-tool files is included by `Electron2D.csproj`. Linux x64 is the currently packaged host; other tool hosts and binary reproducibility across C++ toolchains remain unverified.

## Verification and remaining integration

`RenderingRuntimeTests` exercises both imported languages, material isolation, named parameter lookup, invalid values/types/array sizes, independent copies, disposal, offset/binding changes on reload, and four successive GPU frames checked through framebuffer readback. Uniform changes reuse retained node geometry. The compatibility backend rejects shader materials.

`python3 -B tools/shaders/check.py` verifies reproducible builtin/test artifacts, language diagnostics, bad external SPIR-V, invalid descriptor sets, binding gaps/collisions, oversized buffers and preservation of the previous artifact after failure. Texture checks cover bad sets, gaps, duplicate bindings, arrays, image dimensions, crossed image/sampler pairs and unused resources. Shader sources accompany the embedded `.spv` assets; regenerate each with `dotnet run --project tools/shaders/ShaderImport.csproj -c Release -- <source> <vertex|fragment> <output.spv>`.

RenderingRuntimeTests also checks rejection before payload copying for CreateFromSPIRV, SetSPIRV and the shared import interface. An aligned payload above 16 MiB previously allocated 16,778,560 bytes before throwing. The regression now bounds rejection overhead to less than 64 KiB and verifies that a failed replacement preserves the old program. Structure/reflection still checks the owned snapshot after copying. The updated runtime checks pass with SDL's dummy/software backend; this allocation correction does not establish additional GPU/platform acceptance.

The self-contained Linux x64 ShaderImport publish passes the same import suite from `/tmp` with an empty `PATH` and `LD_LIBRARY_PATH` unset, including byte-for-byte reproduction of the embedded shader programs. Missing packaged tools and a mismatched `v2026.30` version fail before replacing the last usable output. A source archive checksum mismatch fails before extraction/build. `spirv-val --version` records its pinned upstream commit; the upstream archive build initially picked up the enclosing engine Git revision, corrected through its supported build-version override. These checks prove local compiler delivery and import behavior, not additional GPU/backend acceptance.

The published `Electron2D.Shaders.targets` integrates `Electron2DShader` items into SDK C# builds. Items specify the source and vertex/fragment stage, with an optional relative SPIR-V `TargetPath`. Imports run before C# compilation; generated artifacts use the project's intermediate directory, copy into build/publish output and participate in Clean. Native compiler diagnostics fail the build. Invocation uses process arguments without a shell. Normal builds compile and validate every item, so nested includes and macro-only headers remain subject to the compiler's actual resolution rules even with unchanged timestamps. Identical bytecode preserves output timestamps; there is no cache that skips compilation. Publish with `--no-build` consumes previously built artifacts.

`python3 -B tools/shaders/check_build.py --tool <published-importer>` exercises this path in a temporary consumer using only public runtime API: HLSL/GLSL/external bytecode, matching source stems, spaces and shell metacharacters in paths, unchanged outputs, nested guarded includes changed without timestamp changes, corrupt generated output repair, missing includes, invalid external bytecode, duplicate/escaping targets and invalid stages. It also checks Clean without an available importer and a self-contained consumer publish from `/tmp` with `LD_LIBRARY_PATH` unset and empty `PATH`. These checks cover local Linux x64 import/build delivery; they do not add GPU/backend acceptance.

Remaining work includes compressed/integer formats and sampler configuration, further uniform mappings, a shader compilation cache, all unverified target backends. Declaration accounting now covers 2,471 declarations with no unexplained entries; partial behavior remains explicit in the generated coverage tables.

The Linux Shadercross 3.0.0.11 package exports reflection and translation functions, plus the SPIRV-Cross parser. A separate experiment confirmed that reflection accepts an out-of-range OpVectorShuffle component while `spirv-val` rejects it. This establishes the boundary of reflection checks, not a requirement to ship a second runtime validation library. SDL3-CS/Shadercross remains the selected runtime path; no SPIRV-Tools C API or additional validator package is included in the engine.

Texture verification uses fourteen GPU frames per imported language: mip selection, Update, SetImage, HDR preservation, custom snapshot reuse/invalidation, binding reorder on shader reload, defaults/overrides and two distinct sampled textures. Native execution is Linux Wayland/Vulkan only. The SDL_image dependency probe loads the pinned 3.4.6 library, decodes a PNG with alpha, rejects malformed data, repeats decoding after cleanup and verifies that no SDL binding type is exported. It is a backend/package check; the wider Image codec family remains unfinished under ADR 0039, while five loaders and PNG/JPEG saves have separate public API tests. Linux P/Invoke and native extensions share `libSDL3.so.0` through the engine's assembly resolver, avoiding separate copies of SDL for native object ownership.

A self-contained linux-x64 publish of the test executable also passed the five-format public codec checks, PNG/JPEG save checks and both fourteen-frame language texture sequences from `/tmp`, with `LD_LIBRARY_PATH` unset. Loader diagnostics showed a single core library, the published `libSDL3.so.0`. This verifies local package delivery and native behavior; it does not establish AOT, additional codecs, other target platforms or visual owner acceptance.

The fourteenth texture frame uploads pixels decoded by the public `Image.LoadPNGFromBuffer` API from `SavePNGToBuffer`, then checks blue output for both source languages.

The self-contained linux-x64 test publish also passed the complete canvas texture sequence on Wayland and dummy/software from `/tmp` with `LD_LIBRARY_PATH` unset. The publish includes the updated embedded vertex/fragment programs and both imported canvas fixtures. This verifies package delivery for these operations, not AOT or other platforms.

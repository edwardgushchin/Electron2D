# Display server component

Last updated: 2026-10-06

## Scope

This component owns the native SDL video connection, one main window, display and system-theme queries, borrowed operating-system display/window and supported graphics-context identities, cursor and icon resources, clipboard text, IME state, and the event pump. It is the host-facing native boundary before Engine frame scheduling.

## Owned types

[`DisplayServer`](../classes/DisplayServer.md) owns the public display API. Internal [`LinuxPortalThemeSupport`](../classes/LinuxPortalThemeSupport.md) probes the Settings portal at server creation. DisplayServer's public nested enums and the shared FileDialogMode describe feature capabilities, window mode and flags, pointer mode and shape, taskbar progress state, [file-dialog modes](../classes/FileDialogMode.md), and [native handle kinds](../classes/DisplayServer.HandleType.md). The SDL window pointer, cursor handles, and renderer resources remain private; `WindowGetNativeHandle` exposes borrowed operating-system display/window and supported graphics-context identities.

## Runtime flow

1. The SDL main thread calls `Open`, which initializes video and creates one high-density resizable window; on Android, SDLActivity establishes the SDL video thread during initialization and the fullscreen surface supplies the actual size; creation failure unwinds initialization. A visible Wayland window presents a blank surface so the compositor maps it, then refreshes it on pixel-size and scale changes until rendering takes ownership.
2. The host calls `ProcessEvents` before `Engine.AdvanceFrame`. Native queue order is preserved. Keyboard, pointer, wheel, and touch events are converted to typed resources and submitted to `Input` synchronously. `Input` may synthesize touch from mouse or mouse from touch under its documented emulation policies.
3. Window, quit, system-theme change, main-window display-content-scale change, focus, pointer enter/exit, committed text, and composition events reach typed callbacks. `WindowRectChanged` delivers the complete observed client rectangle after each native move or resize, with state committed before the callback. Theme, content-scale, and rectangle notifications retain native queue order. `IsDarkMode` reads current SDL theme state; `IsDarkModeSupported` uses a cached Settings portal capability on Linux Wayland and X11 and current SDL theme state elsewhere. Unchanged rectangles and foreign-window events are ignored. A completed file drop delivers one ordered path list. Focus loss clears touch indexes, invokes the window callback and application notification, then releases pressed input even when a handler fails. Native file-dialog results are copied on SDL's callback thread and delivered on the owner thread during a later event pump.
   On Wayland, IME composition offsets use Unicode codepoints and unknown negative native offsets become zero. The requested client-pixel caret is converted to SDL logical window coordinates using current pixel density before positioning the 1×10 candidate area while text input is active. Native readback passed at densities one and 1.25; actual input-method popup placement remains unverified.
4. The host completes and pumps pending native file dialogs, then disposes the server after stopping its loop. Cursor, window, and video ownership are released, then the process singleton is cleared.

The scene Window now consumes the existing `TextInput` and `TextEditing` events during Engine.Run. DisplayServer commits preedit/selection state before its text callbacks and clears it before a committed string callback; the root SceneTree then notifies live nodes and the focused Control in that order. DisplayServer itself retains only native event/IME ownership. A committed string can contain multiple Unicode scalars and is not assigned to a preceding key event. [TextDeliveryNativeTests](../../tests/Electron2D.Tests/TextDeliveryNativeTests.cs) verifies this bridge on Linux Wayland GPU and compatibility; a real input-method popup remains unverified.

## Dependencies and interactions

Vendored SDL3-CS source supplies internal managed native bindings in `Electron2D.dll`; a target-specific SDL3 library is supplied transitively by the runtime project on Linux. On Linux Wayland and X11, `LinuxPortalThemeSupport` also calls system `libdbus-1.so.3` for a bounded capability probe without an external command or managed package. `DisplayServer` depends on `ElectronObject`, `Input`, `Image`, `Vector2`/`Vector2i`, `Rect2`, and `Rect2i`. `Engine.Run`/`RunAsync` own the ordinary application clock; manual embedding can supply its own elapsed time. RenderingServer owns the active renderer under Engine.Run; Window registers its borrowed native-context query with DisplayServer and removes it at shutdown.

On GNOME Wayland, native-looking client-side title bars require libdecor with its GTK plugin and a GTK backend matching the selected video driver. An inherited `GDK_BACKEND=x11` made `libdecor-gtk` fail initialization and fall back to Cairo. `Open` now updates both native and managed environment values before SDL video initialization and restores the inherited value if startup fails or selects another driver; other driver/backend combinations are unchanged. A process-local GTK style provider extends the selected title-bar background through its border box; it is removed with the window. In a visible Stillglass-Dark session, this removed a transparent one-pixel seam while keeping the themed controls. GTK is optional; without it libdecor may use its fallback decoration.

The native handle query lives in [`DisplayServer.Windows.cs`](../../src/Servers/Display/DisplayServer.Windows.cs). It reads SDL window properties from the [SDL window owned by `DisplayServer`](../../src/Servers/Display/DisplayServer.cs): an X11 `Display*` or Wayland `wl_display*` for `DisplayHandle`, and an X11 window ID, Wayland `wl_surface*`, Win32 `HWND`, or Cocoa `NSWindow*` for `WindowHandle`.

Taskbar progress setters reject Wayland because this host has no verified desktop notification path; SDL's stored success state is insufficient. Other native video drivers delegate to SDL. Visible taskbar progress needs a stable application ID, installed desktop entry, supporting desktop notification consumer, and native acceptance check in a separately approved Linux desktop integration after the application host owns those resources.

## Invariants

One active server and one engine-owned window exist at most. Instance operations, theme and native handle queries, and disposal are owner-thread only; SDL's file-dialog completion callback may run elsewhere but does not invoke game code there. `WindowGetNativeHandle` validates the main-window ID and returns a nonzero borrowed identity or throws; callers must never close or free it, must requery after native window changes, and must stop using it after disposal. The private `SDL_Window*` never crosses the public API. Reentrant pumping and disposal during delivery fail before native state is torn down. Disposal also rejects pending native dialogs and undelivered results. Callback failures are aggregated while later events continue. Native operation failures do not become false success.

The Wayland keyboard-focus screen query and selector return the primary screen because global keyboard focus is unavailable there. Other desktop drivers select the focused main window's center display or fall back to the primary display.

`WindowMoveToForeground` validates the window ID but submits no Wayland activation request, matching the platform's lack of a standard foreground operation. `WindowRequestAttention` submits an activation token without an input serial on Wayland; compositor policy determines any visible urgency indication. Other video drivers delegate foreground and attention requests to SDL and may refuse them.

Wayland display bounds from SDL use logical output dimensions. `ScreenGetSize` and `ScreenGetUsableRect` reconstruct physical output dimensions using the current display mode's pixel density; their position remains the output position. The main-window `ScreenGetScale()` can be fractional, while an explicit screen index rounds that density upward to the integer output scale. A new or hidden window reports the scale currently assigned by SDL; its preferred fractional scale can arrive after initial configuration or first presentation.

Wayland output positions can be logical desktop coordinates while the reported sizes are physical pixels. The resulting rectangles can overlap across monitors with different scales, and `GetScreenFromRect` selects the greatest overlap from those rectangles. This matches the pinned Wayland backend's geometry model on the verified three-monitor host: the compositor reported identical `xdg-output logical_position` and `wl_output.geometry` positions for all three outputs. Other compositors may distinguish those protocol positions.

For one native wheel event, vertical and horizontal input are each attempted even if a callback on the first axis throws. Failures from both axes are retained in the pump's aggregate error. `ScreenGetRefreshRate` uses the current mode's precise rational rate when available and returns `-1` for an invalid screen or unavailable, nonpositive, or nonfinite rate; a valid result is in hertz.

The client rectangle is initialized from the created window and updated from each native move or resize payload before `WindowRectChanged` runs. Its size uses client pixels on Wayland, Android, iOS, tvOS and browsers, from SDL's pixel-size event, and native window units elsewhere. Mouse and touch positions use the same pixel surface; scene viewport transforms convert them to game coordinates. Its position uses platform-native desktop coordinates except on Wayland, where it is conventionally `(0, 0)` because the compositor has no reliable global top-level position. `WindowGetPosition` and `WindowSetPosition` still reject Wayland. The callback runs on the opening thread during either event pump, and handler failures are aggregated after later native events are delivered. Wayland minimum, maximum, and requested window sizes use public client pixels; zero leaves a limit axis unbounded, minimums round upward, maximums round downward, and native SDL logical limits are reapplied after a scale change.

`GetWindowAtScreenPosition` rejects hidden and minimized windows. On X11 it tests half-open client bounds and excludes the native title bar and border; other supported desktop drivers test decorated bounds. Wayland cannot supply the global top-level coordinates needed for this query and is rejected.

`WindowSetCurrentScreen` returns without a native move when the selected display already owns the window. For floating windows on drivers with global positions, it preserves the offset from the old display origin and clamps the requested position into the target work area. Maximized windows are restored, moved, and maximized again; desktop fullscreen uses target display bounds, while exclusive fullscreen selects a mode from the target display. A real relocation is unavailable on Wayland. SDL window-state synchronization is used between dependent maximized transitions, and a failed transition attempts to restore the previous mode.

The native SDL keyboard adapter reads logical `Keycode` from the key event, derives `PhysicalKeycode` from its scancode, and independently derives `KeyLabel` from the scancode under the current layout and the key event's modifier state. Printable non-Latin labels retain their key identity. The physical US bracket positions map to `BraceLeft`/`BraceRight`, the grave position to `Section`, and the ISO key beside left Shift to `QuoteLeft`; common modifier and keypad scancodes have explicit physical mappings. Left and right control, shift, alt, and GUI scancodes set `Location` to the corresponding side on press and release; all other scancodes use `Unspecified`. The modifier bits on a key event exclude that key's own modifier family while preserving other held families; the unmodified SDL state remains available for following pointer events. SDL keypad keycodes are fixed under Num Lock and Shift on the verified Wayland backend, so physical-to-logical and physical-to-label keypad conversion does not yet match the live XKB state; uncommon F25-F35 scancodes are unavailable through SDL. The adapter leaves `Unicode` at zero because SDL key events have no produced text scalar. A separate text-input event may contain multiple scalars or an IME commit and does not identify the producing key press. Filling the scalar requires a native per-key Unicode source with verified IME/composition semantics in the first native keyboard/text adapter slice.

The SDL pointer adapter rejects non-finite mouse positions, relative movement, derived velocity and wheel amount before committing button or timestamp state. The event pump aggregates those failures and continues to later queued events. Finite wheel deltas retain fractional factors on press and release. Captured mode reports zero local/screen cursor velocity while preserving relative motion. A focused `ELECTRON2D_TEST_POINTER_PIXELS=1` Wayland run checks these contracts at pixel density one; fractional density, physical pointer/pen devices and other platforms remain unverified.

The SDL touch adapter rejects duplicate contact beginnings and non-finite normalized or derived position, movement, velocity and pressure before changing its contact table or timestamp. Rejected motion/end events leave the contact available for a later valid event; cancellation releases the index even when a callback fails. `ELECTRON2D_TEST_TOUCH_INPUT=1` checks malformed/valid queue order and index reuse on Wayland with synthetic events. Native double-tap and pen tablet data are separate integrations.

## Current implementation status and exclusions

`CursorSetCustomImage(Resource?, ...)` accepts an Image, readable Texture or null. It copies pixels into an SDL color cursor, accepts fractional hotspot coordinates and truncates them to native pixels. Texture.GetImage returns a temporary owned image; conversion disposes it on success and failure, and rechecks the display lifetime after custom callbacks. Limits and hotspots use actual image pixels, not a texture logical-size override. Empty/unreadable images, unsupported resource types, dimensions above 256×256 and invalid hotspots reject before replacement. Sources remain caller-owned and later mutations need explicit resubmission. Compressed cursor pixels remain blocked on CPU image decompression under ADR 0039.

Window creation, display queries with negative screen selectors and documented invalid-screen fallbacks, native system-theme and screen-wakefulness queries, keyboard-presence probes, basic window policies including native exclusive fullscreen mode selection where supported and ordinary fullscreen mapping on Wayland, clipboard text, pointer modes, standard/custom cursors, image icon submission, IME composition, and keyboard/mouse/touch dispatch exist. Touch availability includes native devices and `Input.EmulateTouchFromMouse`. `IsDarkMode` returns true only for SDL's dark state and requires Settings portal support on Linux Wayland and X11. `IsDarkModeSupported` on Linux Wayland and X11 caches whether the Settings portal interface is available, even when the current preference is unset; other drivers use known SDL light/dark state. A missing session bus, portal, or native D-Bus library yields false. `SystemThemeChanged` forwards SDL notifications through the ordered owner-thread pump; it does not cover every system appearance setting. `HasFeature` reports only capabilities integrated for the current driver or device set. The resize-disabled flag uses the upstream numeric identity and inverse native resizable state. When `HasFeature(MouseWarp)` is true, pointer warping uses the main-window client area; Wayland reports this capability unavailable and `WarpMouse` rejects the request before SDL is called. Wayland pointer position, motion, button, and wheel coordinates use client pixels converted to or from SDL logical coordinates using window pixel density. Operations requiring a global window position reject Wayland. Other drivers use platform-native units; fractional Wayland window and pointer behavior needs native verification. Cursor shapes and pointer modes retain complete numeric identities and reject their terminal markers. All window-flag and window-mode IDs are declared; defined window flags without executable integration throw `NotSupportedException`. On Wayland, Borderless and ResizeDisabled execute; AlwaysOnTop and NoFocus reject before SDL because ordinary top-level windows cannot apply those policies. `WindowIsMaximizeAllowed` checks resize policy regardless of current fullscreen mode, but cannot see compositor `wm_capabilities` yet. Exclusive fullscreen can fail when the display has no suitable mode or the window manager refuses it. Basic native message dialogs and asynchronous file/folder choosers exist; physical Wayland selection returned the chosen button index while closing a one-button message returned zero, which cannot distinguish dismissal from choosing that button. `OpenAny` and MIME-only filters reject use, while Linux accepts and ignores `showHidden`. The first native Linux portal FileChooser bridge must apply MIME filters and verify selection, cancellation, and selected-filter behavior on Wayland; combined file-or-folder selection requires a separately approved chooser capability. Borrowed desktop `DisplayHandle`/`WindowHandle` identities are available for the supported video drivers; unsupported drivers throw `NotSupportedException`, and missing native properties fail explicitly. The exact method-by-method status, missing prerequisites, and implementation triggers are in [the coverage inventory](../coverage/classes/DisplayServer.md). Mouse motion accumulation, explicit flush, mouse/touch emulation, and batched file-drop delivery exist. Deprecated accessibility and global-menu declarations are excluded from this class under [ADR 0041](../decisions/display.md#adr-0041); accessibility and menu capabilities remain future service work. Android display/Activity handles require a graphics host and JNI reference ownership, iOS view-controller handles and macOS/iOS native views require a UIKit/AppKit bridge, and Win32 view access requires a renderer/HDC policy. These belong to the first relevant mobile-host or native-view slices under [ADR 0042](../decisions/display.md#adr-0042). The first compatibility renderer now supplies five Linux GL/EGL/GLX identities with verified window/context ownership, native config/visual queries and borrowed lifetime. Other-platform graphics identities remain incomplete. The scene Window/Engine.Run path owns this renderer; accessibility bridges, native menus, advanced dialogs, speech and mobile hosts remain absent. The Linux x64 executable example packages native SDL; other target packages remain unverified.

On Wayland, `HasFeature(Ime)` and `HasFeature(NativeDialogFile)` currently identify integrated SDL paths without a non-UI probe of text-input-v3 or the Linux FileChooser service. The first native keyboard/text adapter and Linux portal FileChooser slices must add those probes and verify positive and unavailable-service results. Until then, a positive query does not guarantee either operation can complete.

`WindowDpiChanged` forwards SDL's main-window display-content-scale event. It carries no numeric DPI value; callers can query the reported scale after delivery. The callback also runs during `ForceProcessAndDropEvents`, which discards input but retains window events. Initial scale and rectangle ordering with the first rendered buffer remains a renderer integration check.

`WindowRectChanged` replaces split move and resize notifications with one typed full-rectangle callback. The event uses observed native payloads in queue order; a real compositor move/resize sequence and Wayland's zero-position convention still need native verification.

`SetIcon` sets the current main window's default icon until a successful `WindowSetIcon` establishes a window-specific override. On Wayland, nonsquare images are rejected and `HasFeature(Icon)` becomes true only after a native icon request succeeds. Launcher icons and future-window default propagation are outside this one-window host.

## Native controller ownership

The display server owns SDL's gamepad subsystem and each opened gamepad/joystick handle for its own lifetime. It restores the previous SDL background-controller hint on close. Joystick and gamepad events share the ordered `ProcessEvents` pump; recognized devices use the standardized stream and raw joysticks use the joystick stream. Initial devices are registered before the first pump and announced there. Disconnect releases handles and the corresponding Input state; other devices remain active. `ForceProcessAndDropEvents` discards controller input while retaining connection changes. A failing connection subscriber is aggregated after other queued events.

[InputGamepadNativeTests](../../tests/Electron2D.Tests/InputGamepadNativeTests.cs) exercises this ownership on dummy and Linux Wayland using virtual devices. Physical hardware, other platform hosts, Steam/XInput metadata and native allocation behavior remain unverified. Controller motion sensors have a separate prerequisite under [ADR 0038](../decisions/input.md#deferred-coverage-and-exact-implementation-triggers).

## Verification

`env -u LD_LIBRARY_PATH ELECTRON2D_TEST_DISPLAY_WINDOW_EVENTS=1 SDL_VIDEODRIVER=wayland dotnet run --project tests/Electron2D.Tests/Electron2D.Tests.csproj -c Release --no-build` passed after a real compositor close request. The visible window remained alive until the test disposed it. The same session delivered two keyboard-focus gains, one loss, one pointer enter, and one exit through the public typed events. Synthetic dummy and Wayland checks separately cover close/focus/hover queue order, foreign-window filtering, effective hover transitions, pressed-input release after focus loss, and callback failures.

The native Wayland smoke exercised fractional custom cursor hotspots, the accepted 256-pixel image boundary, image-copy lifetime, rejection of nonfinite hotspots and images wider than 256 pixels, shape-slot restoration, and clearing to a system cursor. It compared SDL cursor identities; visual pointer appearance and physical hotspot location were not measured. RenderingRuntimeTests adds ImageTexture/custom Texture conversion, original pixel dimensions despite logical overrides, temporary image cleanup on success/failure, source disposal, shape-slot isolation, invalid/unreadable/disposed resources, off-thread rejection and display disposal during a custom GetImage callback. Those checks run on native Wayland.

The native Wayland smoke compared the public borrowed display and window handles with SDL's exact `wl_display` and `wl_surface` properties; both identities matched and were nonzero.

A focused `WAYLAND_DEBUG=client` probe verified zero activation requests from `WindowMoveToForeground` and one token request, commit, and activation without `set_serial` from `WindowRequestAttention`; both reject a foreign window ID. The probe observes the native request, not a visible compositor attention indicator.

The native Wayland taskbar check passed: both valid setters failed explicitly, invalid arguments and window IDs retained their validation errors, and SDL progress state remained unchanged. It does not prove a visible taskbar indication on any desktop. A supported desktop-entry notification path and non-Wayland acceptance remain unverified.

The separate Linux Wayland screen-blanking native probe passed its false/true/false state checks and a session-bus monitor independently observed the process send matching `UnInhibit`, `Inhibit`, and `UnInhibit` requests to the screen saver service. Physical display timeout was not exercised.

The isolated Wayland and X11 theme smokes passed with a version-two Settings portal and again with `DBUS_SESSION_BUS_ADDRESS` pointing to a nonexistent socket. These checks verify support and unavailable-bus behavior, not an unset color scheme or physical change notification.

An additional hidden Wayland test used a private session bus with a mock Settings portal. Version zero rejected support despite a dark value; version one with an unset value reported support and an unknown SDL theme. Three real D-Bus `SettingChanged` signals drove light, unset, and dark state into SDL before one typed callback per change. The global GNOME preference was not changed; its physical transition remains unverified.

Synthetic close requests on the dummy and real Wayland SDL backends verify main-window ID filtering, queue order relative to quit, no automatic window destruction, delivery while dropping input, and continuation after a throwing callback. The published application also received a real compositor close request from its window control and exited cleanly.

The Wayland native smoke now exercises three connected monitors. One output at 1.25 compositor scale exposes 1536×864 logical bounds and 1.25 mode pixel density, from which the server returns 1920×1080 physical size and indexed scale two. `ScreenGetMaxScale()` is two; a Wayland protocol trace confirmed `wl_output.scale` two for that output and one for each other output. In the latest run the test window landed on the 1.25 output: the native checks passed for pixel size, resize callbacks, pixel-density size and limit conversion, and synthetic pointer-event coordinates. The 320×240 logical window had a 400×300 pixel buffer. The separate visible test consumer rendered a blue SDL software frame; a user moved it from density 1.25 to 1 and back. Two native content-scale events arrived, and client pixel size plus SDL minimum/maximum limits matched the public bounds after each move. This verifies the window-size transition path. Initial fractional scale can be provisional until first presentation; the first renderer integration must verify scale-event ordering there. Synthetic native IME events check composition and commit state before callbacks, and native window checks cover focus, size constraints, borderless and resize-disabled toggles, maximized and fullscreen restoration, and exclusive-as-ordinary fullscreen mapping. A targeted Wayland run passed topmost/focus rejection without native flag mutation and the mode-independent maximize approximation; the full native smoke passed twice after the initial-scale expectation was corrected. A minimized Wayland window cannot reliably be restored programmatically; the minimization check runs last. Real IME UI and unexercised compositor transitions remain open.

The native Wayland pointer check observes all five requested modes and SDL cursor/grab state. Synthetic motion, button, and wheel events passed the pixel-coordinate adapter at density 1.25. A separate visible-window test passed real focused motion and left-button press/release against SDL's state, plus real relative motion under `Captured`. During a 25-second `Confined` check, the user pushed the pointer toward all four edges of a 600×450 client area: its x range was 0…599 and y range 0…449, and mouse focus never left the window. An earlier focused `WarpMouse` call briefly changed SDL's reported position to the requested target while the compositor left the physical pointer elsewhere. Wayland no longer calls SDL for this unsupported capability: `HasFeature(MouseWarp)` is false and the call raises `NotSupportedException` without synthetic movement. Physical warp on advertised desktop drivers remains unverified. A visible, keyboard-focused child process matched the parent's stable nonempty clipboard and primary selection through read-only checks; IPC exposed only match booleans and lengths. A hidden child had received no Wayland selection offers because it lacked keyboard focus. A private headless Mutter compositor did not focus the SDL publisher or deliver an input serial, so the setter was not exercised. Cross-process publication requires an isolated compositor with an input-capable seat that focuses publisher and reader, delivers a recent serial, and owns both selections without changing the user's clipboard.

## Windowed lifecycle

Window now delegates native operations to DisplayServer under Engine.Run. Startup happens before scene ready, teardown after scene finalization. The manual DisplayServer API remains available. Native backend event probes live in tests, including WindowRuntimeTests; examples no longer own a duplicate frame loop.

Graphics handle verification uses `ELECTRON2D_TEST_RENDER_HANDLES=1`: Wayland EGL/GL and EGL/GLES, XWayland GLX, native identity checks, a foreign context/config, unchanged pixel output, thread/ID/disposal rejection and reopen. A forced X11/EGL GLES probe failed native surface creation before handle queries. Other platforms remain unverified.

# CanvasItem contract audit

Last updated: 2026-10-26

The abstract [CanvasItem](../classes/CanvasItem.md) supplies the common canvas contract to the spatial `Entity` and rectangular `Control` branches under [ADR 0008](../decisions/scene.md#adr-0008). Its own type row is separate from inherited [Node](../coverage/classes/Node.md) and [Object](../coverage/classes/Object.md) requirements. Closing this type must not close either ancestor or the complete physics backend acceptance gate.

## Processing access

Logical metadata reads permit the scene owner or any active processing group. This includes modulation, borrowed material, light/visibility masks, Z/Y order, behind-parent and parent-material flags, texture sampling, scale oversampling, local/effective visibility and logical canvas/item identities. Callers coordinate writes, configuration and lifetime changes; separate reads are not an atomic scene snapshot. Ordinary unrelated threads have no group permission. The existing unguarded TopLevel stored-value getter retains its contract.

The owner or the item's current processing group may author the rendering metadata above, request redraw and read/write typed instance parameters. The instance getter may prepare its retained typed storage, so it uses current-group access. The common metadata guard checks disposal, capture, current-group access and the existing virtual mutation validator before even equal assignments. It preserves render invalidation without numerical authoring preflight or waking a body. Warning/property-list callbacks remain synchronous on the caller and receive no additional native or numerical permissions.

Visible/Show/Hide transitions, TopLevel rebinding, sibling ordering, hierarchy, drawing-command recording and raw RenderingServer operations retain owner-thread access. Logical item identity creation uses the existing item gate and weak registry; it creates no native resource. Native mouse queries retain their individual owner guard. Existing transform-notification, physical-publication and direct-space rules remain independently applicable.

The scene joins each worker stage before rendering or reading numerical results. A renderer therefore consumes completed frontend edits. These permissions do not make arbitrary concurrent mutation of a material, mesh, texture, tile resource or another group safe.

## Material scratch lifetime

GPU rendering previously removed per-material sampler-binding and swizzle arrays after a single unused frame. An alternating visible/culled shader material consequently allocated 40 plus 32 managed bytes each time it returned, despite reusing the same material and native pipeline. The backend now retains these CPU arrays in existing-platform weak-key tables for the lifetime of `MaterialState`. Values contain raw bindings/maps, own no native resources and do not retain their material keys. Texture bindings are refilled before use, including particle compute consumers. Backend disposal clears both tables.

Native texture/sampler/pipeline ownership and eviction remain unchanged. A longer cold hidden interval can retire a custom pipeline and its return can allocate. The regression prepares that eviction/reconstruction before measuring repeated one-hidden-frame cycles; it does not claim that arbitrary cold material reappearance is allocation-free.

## Verification receipts

`CanvasItemContractTests.Run` checks custom/UI/physical ancestry, transforms, copied input localization, enter/exit/reentry, canvas-filtered point queries, stable body/item identities, foreign-group observations, current-group metadata writes, high visibility bit 31, typed values, derived mutation rejection and forbidden native/hierarchy-sensitive operations. It measures 128 complete moving PhysicsFrame intervals after 128 warm intervals with exact zero owner/all-thread managed bytes. Shapes/materials remain borrowed across scene disposal.

`RunNative` uses the public Engine.Run loop, actual moving physical bodies and a real process-group worker. It checks red, modulated and culled pixels, including actual declared GLSL/HLSL instance parameters. The native fixture requests a 320x240 client and asserts that prepared size throughout measurement. A smaller 96x80 candidate was rejected: the Wayland compositor asynchronously raised its width to 224 during the idle measurement, correctly allocating replacement targets. A calibrated allocation profiler and per-frame dimension observations attributed the 640 bytes to CanvasBackend.Target/PreparePresentation and GPUCanvasBackend.CreateGPUTarget. This is cold resize work, outside the stable-size claim.

Each 224-frame lifecycle contains 64 active plus 64 idle measured intervals from the public pre-frame callback through FramePostDraw, including scheduling, physics, process and rendering. Input/picking and the longer cold material cycle are prepared before the measured interval. Pixel tolerance is 0.03 per RGBA8 RGB channel; transform/localization tolerance is 0.001 scene units. These tolerate raster/channel rounding and affine float arithmetic, never a missing collider, wrong identity, tick or callback count.

Current-source receipts, source/PDB/resource proofs, native compiler inputs and rejected candidates are retained under `bin/physics-canvas-item-contract/2026-10-26/`. `validation.json` records 60 fresh source-bound profiles: 55 passed, four returned the expected software PremultAlpha capability error, and one CLR/compatibility SDL-GPU/CPU-owner profile failed its complete-frame all-thread budget with active 0/32 and idle 0/0 bytes. The failure remains unqualified. Its API/pixel path passed in strict NativeAOT and in a separate calibrated CLR diagnostic; the 32-byte observation has not been attributed and is not dismissed as runtime bookkeeping. The functional type status therefore does not certify this allocation gate.

The matrix exercises 8,960 rendered frames, 5,120 measured native intervals and 2,048 complete headless physical intervals. Of the native intervals, 4,992 have strict zero owner/all-thread bytes; the remaining 128 belong to the failed profile. Four existing managed lifecycle/visibility/modulation/polygon selectors, native particle material texture/allocation consumers and an eight-process CPU-contention control add seven successful controls. The particle check reports 32 warmed render/process/sort frames at zero managed bytes; it has its own narrower bracket. CLR and NativeAOT PDBs match all 2,663 current runtime source files and the five focused fixture sources; both embedded GLSL/HLSL fixture modules match their tracked SPIR-V. This functional cohort does not measure isolated solver speed, native heap allocations, mass-scene GPU advantage, cross-platform behavior or human visual acceptance. ## Allocation failure attribution

The native fixture retains each of its 128 measured frame deltas, the authoring callback's own allocation delta and managed thread ID, collection-count changes, runtime version and GC mode. It reports nonzero samples after the measured intervals and keeps the strict owner/all-thread budget. Callback measurements exclude worker dispatch before/after that callback; the complete-frame global counter still includes those operations. Collection counts supply context, not a validity filter.

For an explicitly profiled CoreCLR process, the fixture reuses `PhysicsAllocationTrace` and the existing `ELECTRON2D_POINT_ALLOCATION_TRACE` setting. `CORECLR_ENABLE_PROFILING=1`, the calibrated profiler GUID/path and a fresh `E2D_ALLOCATION_TRACE` prefix remain required. The canvas uses tag domain `0x200000000`; each measured frame uses offset `500 + frame - 96`, separately from positive/empty controls. BEGIN precedes both initial counters and END follows both final counters. A `finally` closes an entered bracket if Engine.Run fails before FramePostDraw. The earlier temporary diagnostic ended its event bracket before the final counter reads; it cannot establish absence of events in the missing suffix.

Normal execution loads no profiler. NativeAOT and a CLR process without explicit profiling reject tracing before scene/physics/native-window authoring. The shared helper's standalone ABI calibration and in-process owner positive/empty controls accompany traced results. Renderer selection, 224 frames, 160 authoring callbacks, 64 active/64 idle intervals, fixed client size, GC preparation, pixels and zero-byte limits remain unchanged.

The first integrated controls under `bin/physics-canvas-allocation32/2026-10-26/` pass the unchanged frozen original profile, three ordinary CLR profiles, three traced CLR profiles (including CPU contention and separate GPU physics), and three ordinary strict NativeAOT profiles. All actual native measurement tags have zero ObjectAllocated events in those three traced runs. These observations do not attribute or clear the original untraced 32-byte result; the historical failed allocation gate remains open.

A separately compiled positive-control copy adds one no-inline `byte[1]` allocation to the authoring callback at frame 100, leaving the runtime unchanged. The strict gate rejects it and reports owner/all/worker `0/32/32`, managed owner/worker IDs, GC `0/0/0`, and the exact native tag. The profiler records one raw size-25 object in that tag, aligned to the counter's 32 bytes, with `AllocateProbe` and the worker-processing stack. All 290 entered native brackets balance even on this expected failure. The injected source is an ignored diagnostic artifact, not production fixture behavior or a qualified zero-allocation result.

After integrating independent accessibility work, two CLR profiles and one NativeAOT profile also pass against their separately frozen source cohort. The receipt now contains 13 successful native-window controls (1,664 complete measured intervals), two explicit tracing-configuration rejections and the deliberate allocation rejection. Four normal traced processes plus that failing positive control retain 1,450 balanced native brackets; none of the normal measured tags contains an object event. Initial runtime PDBs bind 2,663 sources, integrated PDBs bind 2,668, and each focused fixture binds four authored sources plus its two shader resources. `validate.py` checks the counters, positive/empty controls, bracket balance, expected failures and payload/source identities without changing the old failed result.
